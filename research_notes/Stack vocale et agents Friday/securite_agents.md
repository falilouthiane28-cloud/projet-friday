# Sécurité d'un agent IA personnel « always-on » sur macOS (état de l'art, novembre 2026)

Périmètre : agent personnel avec accès fichiers / e-mail / shell / domotique, cible macOS (Apple silicon, macOS 26 « Tahoe »), Python 3.11+. Les notes sont datées : tout ce qui est antérieur à 2025 est explicitement signalé comme « ancien ». Les sources primaires (Willison, DeepMind, OWASP, Anthropic, Apple, Docker, E2B) ont été relues directement ; les chiffres uniquement rapportés par des blogs tiers sont marqués « non vérifié ».

## Question 1 — Défenses contre l'injection de prompt : Dual-LLM, CaMeL, « lethal trifecta », passerelles d'outils à capacités, validation des sorties ; publications / produits 2025-2026

### Takeaway
Le consensus 2025-2026 (Willison, DeepMind, Meta, Anthropic, OpenAI, OWASP) est que l'injection de prompt n'est pas « résolue » par les modèles ni par des détecteurs ; la seule défense fiable est **architecturale** : empêcher qu'une entrée non fiable puisse déclencher une action conséquente (séparer flux de contrôle et flux de données, capacités attachées aux données, casser la « trifecta »). Les classificateurs et l'entraînement des modèles ne sont qu'une couche additionnelle qui fait baisser le taux de succès (≈ 1-2 % dans le meilleur cas publié par Anthropic), jamais une garantie.

### Cited Findings

**Lethal trifecta (Willison, juin 2025)**
- Définition : un agent devient exploitable dès qu'il combine (1) accès à des données privées, (2) exposition à du contenu non fiable, (3) capacité de communiquer vers l'extérieur. « If your agent combines these three features, an attacker can easily trick it into accessing your private data and sending it to that attacker. » — [Simon Willison, The lethal trifecta (16 juin 2025)](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Cause racine : « LLMs are unable to reliably distinguish the importance of instructions based on where they came from. » — [même source](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Cas réels cités : Microsoft 365 Copilot, serveur MCP officiel GitHub, GitLab Duo (2025) ; plus anciens (2023-2024) : ChatGPT, Google Bard, Amazon Q, Slack, app iOS Claude. — [même source](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Position sur les « guardrails » vendeurs : un produit qui bloque « 95 % des attaques » est, en termes de sécurité applicative, « very much a failing grade ». — [même source](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Pour l'utilisateur final qui combine lui-même des outils (MCP…), « the only way to stay safe there is to avoid that lethal trifecta combination entirely ». — [même source](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Couverture 2026 : une note de recherche de la Cloud Security Alliance (citant un « AI Risk Quadrant Q2 2026 » sur 100 agents) rapporte que 98 % des agents évalués réunissent les trois conditions et que 11 % seulement passent un benchmark de base — chiffres issus d'un rapport tiers, **non vérifiés**. — [CSA research note](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-agent-lethal-trifecta-capability-securi)

**Meta « Agents Rule of Two » (31 oct. 2025)**
- Règle : tant que la détection fiable d'injection n'existe pas, un agent ne doit satisfaire **au plus deux** des trois propriétés dans une même session : [A] traiter des entrées non fiables, [B] accéder à des systèmes sensibles / données privées, [C] changer un état ou communiquer vers l'extérieur. Si une tâche exige les trois, l'agent ne doit pas tourner de façon autonome : supervision humaine ou validation fiable ; un contexte neuf peut séparer les propriétés entre sessions. — [Meta AI, Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)
- Inspiré explicitement de la « Rule of 2 » de Chromium et de la trifecta de Willison ; présenté comme complément (pas substitut) du moindre privilège et de la défense en profondeur. — [même source](https://ai.meta.com/blog/practical-ai-agent-security/)

**Dual-LLM (Willison, 2023 — ancien) et ses limites**
- Motif original : un LLM « privilégié » (P-LLM) avec outils délègue tout texte non fiable à un LLM « en quarantaine » (Q-LLM) sans outils ; le P-LLM ne voit jamais le contenu brut. Willison reconnaît en 2025 une faille : si le P-LLM demande au Q-LLM d'extraire « l'adresse de Bob », une injection peut substituer l'adresse de l'attaquant et exfiltrer le document. — [Willison, analyse de CaMeL (11 avr. 2025)](https://simonwillison.net/2025/Apr/11/camel/)

**CaMeL — Google DeepMind, « Defeating Prompt Injections by Design » (arXiv 2503.18813, v1 24 mars 2025, v2 24 juin 2025)**
- Auteurs : Debenedetti, Shumailov, Fan, Hayes, Carlini, Fabian, Kern, Shi, Terzis, Tramèr. Couche de protection **système** autour du LLM : « explicitly extracts the control and data flows from the (trusted) query », de sorte que les données non fiables ne peuvent pas modifier le flux du programme ; utilise des **capabilities** pour empêcher l'exfiltration via des flux non autorisés. Résultat AgentDojo : 77 % des tâches résolues **avec sécurité prouvable** contre 84 % sans défense. Code : github google-research/camel-prompt-injection. — [arXiv 2503.18813](https://arxiv.org/abs/2503.18813)
- Mécanique (lecture Willison) : le P-LLM traduit la requête utilisateur en un **dialecte Python restreint** exécuté par un interpréteur maison ; chaque valeur porte des métadonnées de provenance / permissions (capabilities) ; des **politiques** gèrent les actions (ex. : envoyer un e-mail seulement si le destinataire est de confiance, sinon demander à l'utilisateur) ; le Q-LLM peut être petit / local et le P-LLM cloud ne voit jamais les sorties d'outils ; pas de modèle de détection — « security engineering » classique. — [Willison, CaMeL](https://simonwillison.net/2025/Apr/11/camel/)
- Limites assumées : §8.3 du papier, « prompt injection attacks are not fully solved » ; les utilisateurs doivent écrire et maintenir des politiques (risque de fatigue d'approbation). — [même source](https://simonwillison.net/2025/Apr/11/camel/)

**Six design patterns (Beurer-Kellner, Tramèr, Debenedetti et al., arXiv 2506.08837, juin 2025)**
- Principe central : une fois une entrée non fiable ingérée, « it must be constrained so that it is *impossible* for that input to trigger any consequential actions ». — [arXiv 2506.08837 (HTML v3)](https://arxiv.org/html/2506.08837v3)
- Les six motifs : (1) **Action-Selector** — le LLM choisit parmi des actions prédéfinies, sans retour d'information ; (2) **Plan-Then-Execute** — la séquence d'appels d'outils est figée avant toute lecture de données non fiables ; (3) **LLM Map-Reduce** — des sous-LLM isolés traitent chaque élément non fiable avec sorties contraintes, puis agrégation ; (4) **Dual LLM** — P-LLM / Q-LLM, résultats manipulés par référence ; (5) **Code-Then-Execute** — l'agent écrit un programme qui appelle outils et sous-LLM (c'est CaMeL) ; (6) **Context-Minimization** — le contenu est retiré du contexte dès qu'il a servi. — [même source](https://arxiv.org/html/2506.08837v3)

**OWASP Top 10 for Agentic Applications 2026 (publié 9 déc. 2025, > 100 contributeurs)**
- Page officielle (date, processus). — [OWASP GenAI](https://genai.owasp.org/resource/2025-12-09/owasp-top-10-for-agentic-applications-for-2026)
- Liste (résumé secondaire fidèle) : ASI01 Agent Goal Hijack ; ASI02 Tool Misuse & Exploitation ; ASI03 Identity & Privilege Abuse ; ASI04 Agentic Supply Chain ; ASI05 Unexpected Code Execution (RCE) ; ASI06 Memory & Context Poisoning ; ASI07 Insecure Inter-Agent Communication ; ASI08 Cascading Failures ; ASI09 Human-Agent Trust Exploitation ; ASI10 Rogue Agents. — [Cycode, résumé OWASP ASI](https://cycode.com/blog/owasp-top-10-agentic-applications/)
- Mitigations retenues : ASI01 séparer instructions et contenu récupéré, contraindre l'agent indépendamment du contexte, confirmation humaine pour actions sensibles ; ASI02 scoper chaque outil au minimum, valider strictement les paramètres, policy check à chaque invocation ; ASI05 exécuter le code dans des conteneurs à moindre privilège, **egress réseau refusé par défaut**, APIs paramétrées plutôt que shell brut ; ASI09 confirmations qui montrent **l'action brute** (pas le résumé de l'agent), journaux immuables de « ce qui a été affiché vs ce qui a été exécuté ». — [même source](https://cycode.com/blog/owasp-top-10-agentic-applications/)

**Anthropic**
- « Mitigating the risk of prompt injections in browser use » (24 nov. 2025) : défense en couches = entraînement RL sur injections simulées + classificateurs sur le contenu non fiable entrant dans le contexte + red teaming. Taux de succès d'attaque (attaquant adaptatif Best-of-N, 100 essais / environnement) : Opus 4.5 8,0 % (modèle seul) → 1,4 % avec safeguards améliorés ; Sonnet 4.5 13,8 % → 1,9 % ; Haiku 4.5 12,0 % → 2,4 %. « No browser agent is immune to prompt injection » ; 1 % reste « meaningful risk ». — [Anthropic, prompt injection defenses](https://www.anthropic.com/research/prompt-injection-defenses)
- « Trustworthy agents » (9 avr. 2026) : quatre couches où se joue la sécurité — modèle, **harness**, outils, environnement ; « a well-trained model can still be exploited through a poorly configured harness, an overly permissive tool, or an exposed environment » ; « no single line of defense is enough to guarantee protection » ; recommandation aux développeurs : être délibéré sur outils, données, permissions et environnements accordés. — [Anthropic, trustworthy agents](https://www.anthropic.com/research/trustworthy-agents)
- Chiffres 2026 cités par des tiers (Opus 4.6 : 0 % sur 200 essais en environnement de codage contraint, mais 78,6 % sans safeguards / 57,1 % avec, en environnement GUI à 200 essais) — **non vérifiés** contre la system card. — [recherche web, voir NeuralTrust](https://neuraltrust.ai/blog/claude-opus-4-6-safety)

**OpenAI**
- Page « Prompt injections » : entraînement à distinguer instructions fiables / non fiables, scan automatisé en temps réel, et OpenAI admet que l'injection « is unlikely to ever be fully 'solved' ». — [OpenAI, prompt injections](https://openai.com/safety/prompt-injections/)

**OpenClaw (agent personnel open source, ex-Clawdbot) — cas d'école 2026**
- Zenity : une injection indirecte a pu faire ajouter par l'agent une intégration de chat contrôlée par l'attaquant (backdoor zéro-clic). — [Zenity Labs](https://labs.zenity.io/p/openclaw-or-opendoor-indirect-prompt-injection-makes-openclaw-vulnerable-to-backdoors-and-much-more)
- Imperva : injections cachées dans des **noms de contact** et **labels de localisation** passés au modèle sans que l'utilisateur les voie ; OpenClaw 2026.4.23 a déplacé ces champs dans un canal « untrusted metadata » séparé. — [Imperva](https://www.imperva.com/blog/compromise-openclaw-with-prompt-injections-in-message-objects/)
- Snyk : la surface d'injection inclut pages web, corps d'e-mails, pièces jointes, logs collés ; l'agent a un accès shell. — [Snyk](https://snyk.io/articles/clawdbot-ai-assistant/)
- Cisco : un skill tiers faisait exfiltration + injection à l'insu de l'utilisateur ; l'autorité néerlandaise de protection des données a déconseillé le déploiement sur des systèmes sensibles. — [TechRadar](https://www.techradar.com/pro/here-are-the-openclaw-security-risks-you-should-know-about)
- Survey académique (25 mai 2026) : « Security of OpenClaw Agents: Fundamentals, Attacks, and Countermeasures » — skill poisoning, manipulation cognitive, cascades multi-agents, chaîne d'approvisionnement ; mémoire persistante + privilèges élevés = surface élargie. — [arXiv 2605.25435](https://arxiv.org/abs/2605.25435)

### Inferences
- Pour « Friday » (fichiers + e-mail + shell + domotique), la trifecta est réunie par construction. Le design doit donc **casser une branche par session / par tâche** : par exemple, la session qui lit des e-mails (non fiable) n'a pas d'outil d'envoi ni de shell ; la session qui envoie / exécute ne reçoit que des **références** (identifiants, variables typées) et non le texte brut.
- Implémentation pragmatique en Python 3.11+ d'un « CaMeL light » : (a) le planificateur (P-LLM) ne reçoit que la requête utilisateur et produit un plan sous forme de données structurées (JSON / liste d'appels typés) ; (b) chaque valeur issue d'un outil est encapsulée dans un objet `Tainted(value, sources)` ; (c) un **gateway d'outils** vérifie, avant chaque appel, une politique du type « aucun argument `to`, `url`, `cmd` ne peut dériver d'une source non fiable sans approbation humaine » ; (d) le Q-LLM (petit modèle local) ne reçoit que du texte et retourne des schémas contraints (Pydantic). C'est le motif Code-Then-Execute + Dual LLM.
- Validation des sorties : forcer des schémas stricts (enum pour les actions, regex pour les identifiants) sur les sorties du Q-LLM réduit le canal d'injection à ce que le schéma autorise (motif Map-Reduce « constrained outputs »).
- Les classificateurs (Anthropic, OpenAI, Claude Code « server-side probe ») valent comme **télémétrie et friction**, pas comme frontière de sécurité ; ne pas s'appuyer dessus pour autoriser une action irréversible.
- Les métadonnées « invisibles » (noms de contacts, objets de calendrier, titres de fichiers, noms de périphériques domotiques) sont des vecteurs d'injection avérés (Imperva) : tout champ provenant d'un système externe doit être marqué non fiable, même s'il semble structurel.

### Gaps
- Je n'ai pas pu lire le document OWASP complet (PDF derrière un lien de téléchargement) ; la liste ASI et les mitigations viennent d'un résumé secondaire concordant avec plusieurs autres.
- Pas de source primaire pour les chiffres 2026 des system cards Anthropic (Opus 4.6, Sonnet 4.6) ni pour le « 99,5 % » revendiqué pour ChatGPT agent ; uniquement des reprises tierces.
- Aucune implémentation Python « prête à l'emploi » de CaMeL en production identifiée au-delà du dépôt de recherche google-research/camel-prompt-injection (non inspecté dans cette session).

## Question 2 — Niveaux « human-in-the-loop » et matrices d'approbation dans les produits réels (Claude Code, OpenAI Operator / ChatGPT agent, OpenClaw, OpenJarvis)

### Takeaway
Les produits convergent vers une matrice à trois valeurs par action (**allow / ask / deny**) évaluée dans un ordre fixe (deny > ask > allow), des **modes** globaux (manuel, accept-edits, plan, auto avec classificateur, dontAsk pour CI, bypass réservé aux VM isolées), des **chemins protégés** jamais auto-approuvés, et une **approbation obligatoire** avant toute action irréversible ou transaction, avec « watch mode » sur les sites sensibles. Point clé : les règles sont appliquées par le **harness**, pas par le modèle.

### Cited Findings

**Claude Code (docs officielles, lues en nov. 2026)**
- Tableau par type d'outil en mode Manuel : lecture seule → pas de prompt (dans les répertoires de travail) ; Bash → prompt sauf ensemble intégré de commandes read-only ; modification de fichiers → prompt (mémorisé jusqu'à fin de session) ; WebFetch → prompt sauf domaines de doc pré-approuvés ; WebSearch → prompt. — [Claude Code, Configure permissions](https://code.claude.com/docs/en/permissions)
- Ordre d'évaluation : « Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome » ; un allow ne peut pas creuser une exception dans un deny. Un deny sur le nom nu d'un outil (`Bash`) **retire l'outil du contexte** du modèle. — [même source](https://code.claude.com/docs/en/permissions)
- « Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what Claude Code allows. » — [même source](https://code.claude.com/docs/en/permissions)
- Syntaxe : `Bash(git commit *)`, `Read(./.env)`, `Read(./secrets/**)`, `WebFetch(domain:github.com)`, `Tool(param:value)`, globs sur noms d'outils (`mcp__*`). Les règles Bash matchent les sous-commandes composées, substitutions `$(...)`, boucles ; elles ne matchent pas le même programme invoqué autrement (chemin absolu, `sh -c`) — d'où la recommandation de **coupler avec le sandbox** et des hooks `PreToolUse`. — [même source](https://code.claude.com/docs/en/permissions)
- Modes : `default` (Manuel : lectures seulement sans demander) ; `acceptEdits` (édits + `mkdir/touch/mv/cp` dans le répertoire de travail) ; `plan` (explore, n'édite pas) ; `auto` (« A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read » — « does not guarantee safety ») ; `dontAsk` (tout ce qui demanderait est refusé : CI) ; `bypassPermissions` (« Only use this mode in isolated environments like containers, VMs, or dev containers without internet access » ; « offers no protection against prompt injection »). Les deny s'appliquent dans tous les modes, y compris bypass. — [Claude Code, Permission modes](https://code.claude.com/docs/en/permission-modes)
- Classificateur du mode auto : ordre fixe — règles explicites, puis actions locales sûres auto-approuvées, puis tout le reste au classificateur ; les allow trop larges (`Bash(*)`, `Bash(python*)`) sont **ignorés** en mode auto ; blocages par défaut : `curl | bash`, force push, déploiements prod, destruction irréversible ; après 3 blocages consécutifs ou 20 au total, retour aux prompts. — [même source](https://code.claude.com/docs/en/permission-modes)
- Safeguards anti-injection : « Tool results are stripped from those requests, so hostile content in a file or web page can't manipulate the classifier directly » ; « A separate server-side probe scans incoming tool results and flags suspicious content before Claude reads it » ; les rapports de sous-agents suspects sont préfixés d'un avertissement ; une limite énoncée en conversation peut être perdue à la compaction — « For a hard guarantee, add a deny rule instead ». — [même source](https://code.claude.com/docs/en/permission-modes)
- Chemins protégés (jamais pré-approuvés par un allow) : `.git`, `.claude`, `.vscode`, `.idea`, `.husky`, `.devcontainer`, `.bashrc/.zshrc/.profile`, `.npmrc`, `.gitconfig`, `.mcp.json`, `.claude.json` ; chemins « critiques » (racine, home, répertoire de travail et parents) protégés de `rm`/`rmdir` ; « The check can miss some commands, so it doesn't replace an operating-system control such as sandboxing. » — [même source](https://code.claude.com/docs/en/permission-modes)
- Anthropic (avr. 2026) : permissions par action « always allow, needs approval, or block » ; Plan Mode montre tout le plan d'un coup plutôt que d'approuver action par action ; taux de « check-in » du modèle sur tâches complexes ≈ doublé, interruptions utilisateur en légère hausse seulement. — [Anthropic, trustworthy agents](https://www.anthropic.com/research/trustworthy-agents)

**OpenAI Operator → ChatGPT agent**
- Lancement Operator (jan. 2025, **ancien**) : demande d'approbation « before finalizing any significant action, such as submitting an order or sending an email » ; sur sites sensibles (e-mail, finance) supervision rapprochée ; modèle de surveillance qui met en pause si contenu suspect à l'écran. — [OpenAI, Introducing Operator](https://openai.com/blog/introducing-operator)
- System card (addendum mai 2025) : quatre couches — confirmations, Watch Mode, refus des tâches à haut risque (transactions bancaires…), **prompt injection monitor** qui ingère la capture d'écran. Operator a ensuite été fondu dans « ChatGPT agent mode » (juil. 2025). — [o3 CUA system card (PDF)](https://cdn.openai.com/pdf/4375e605-f9a6-438d-bcc8-190599c183a6/o3_cua_system_card.pdf) ; [OpenAI, prompt injections](https://openai.com/safety/prompt-injections/)
- Test indépendant (Willison, oct. 2025, sur Atlas) : ni GitHub ni une banque en ligne n'ont déclenché le « watch mode » lors de son test ; il refuse de le compter comme mitigation tant qu'il ne l'a pas vu fonctionner. — [Willison sur le CISO d'OpenAI / Atlas](https://feeds.simonwillison.net/2025/Oct/22/openai-ciso-on-atlas/)

**OpenClaw**
- Doc sécurité officielle : « OpenClaw ships with conservative defaults » ; gateway lié à loopback ; « not a hostile multi-tenant security boundary » ; expéditeurs DM inconnus reçoivent un **code d'appairage** plutôt que de voir leur message traité ; deux couches d'allowlists ; profils par agent, mode lecture seule, sandboxing documenté ; commande `openclaw security audit` pour détecter la dérive de configuration. — [OpenClaw, gateway security](https://docs.openclaw.ai/gateway/security)
- Varonis : des requêtes de type phishing en anglais courant passaient les règles de vérification ; un attaquant imitant le **display name** d'un utilisateur autorisé contournait l'allowlist (corrigé). — [DEV Community / Varonis](https://dev.to/etairos/openclaw-ai-agent-exploited-through-hidden-contact-prompts-and-social-engineering-21di)

**OpenJarvis**
- Framework « local-first » ; couche de sécurité qui scanne prompts et sorties pour secrets, PII et chemins sensibles, avec un mode `block` qui interrompt le traitement ; audit logger vers une base locale. Aucun audit externe ni rapport de vulnérabilité trouvé. — [OpenJarvis, user guide security](https://open-jarvis.github.io/OpenJarvis/user-guide/security)

### Inferences
- Matrice d'approbation recommandée pour Friday (synthèse des pratiques) :
  - **Tier 0 — auto** : lectures locales dans des répertoires déclarés, recherche, calcul, lecture de capteurs domotiques.
  - **Tier 1 — auto + journal** : écritures dans un espace de travail dédié, brouillons d'e-mails (non envoyés), commandes shell d'une allowlist étroite exécutées **dans le sandbox**.
  - **Tier 2 — demander (afficher l'action brute)** : envoi d'e-mail / message, commande shell hors allowlist, écriture hors espace de travail, actionneurs domotiques (serrure, chauffage, alarme), requêtes HTTP vers un domaine hors allowlist.
  - **Tier 3 — refuser toujours** : secrets (`~/.ssh`, `~/.aws`, Keychain, `.env`), `rm` sur chemins critiques, modification de la configuration de l'agent lui-même (équivalent des « protected paths »), `curl | sh`, désactivation du sandbox.
- Reproduire le principe « deny > ask > allow, premier match gagne », et appliquer les deny dans tous les modes, y compris un éventuel mode « autonome nocturne ».
- Les confirmations doivent présenter l'action réelle (commande, destinataire, payload) et non la paraphrase du modèle (OWASP ASI09) ; journaliser ce qui a été affiché à l'utilisateur et ce qui a été exécuté.
- Un classificateur d'approbation (type mode auto) peut être ajouté comme **couche de confort**, à condition de ne jamais lui transmettre les résultats d'outils bruts (leçon Claude Code).

### Gaps
- Le system card Operator (page openai.com) a renvoyé 403 ; les détails viennent de la page « Introducing Operator », du PDF o3-CUA et de résumés tiers. Le chiffre « 62 % → 23 % » de susceptibilité est rapporté par un blog, non vérifié.
- Je n'ai pas trouvé de documentation OpenClaw détaillant un flux d'« exec approval » par action (la page sécurité renvoie à des sous-pages non lues).

## Question 3 — Secrets sur macOS : Keychain via Python (keyring) vs coffre chiffré ; ne jamais exposer les clés au contexte du LLM

### Takeaway
`keyring` (25.7.0, nov. 2025) fournit un accès simple au Keychain macOS, mais tout script lancé par **le même binaire Python** lit les secrets sans prompt ; le contrôle d'accès biométrique (Touch ID) exige la « data-protection keychain » et un binaire signé avec entitlements, donc hors de portée d'un script Python non signé. La pratique émergente 2025-2026 est un **broker de secrets** hors du processus de l'agent qui injecte les clés dans l'environnement du sous-processus ou directement dans les requêtes réseau (proxy), de sorte que le LLM ne voit jamais la valeur.

### Cited Findings
- `keyring` 25.7.0 (16 nov. 2025) ; backend macOS `keyring.backends.macOS.Keyring` ; API `keyring.set_password("system","username","password")` / `get_password` ; nécessite Python ≥ 3.9 et, pour le backend Keychain, macOS 11+ et un Python « universal2 » ≥ 3.8.7. — [PyPI keyring](https://pypi.org/project/keyring/)
- Caveat officiel : « any Python script or application can access secrets created by keyring from that same Python executable » sans prompt OS ; pour forcer un prompt à chaque accès, retirer Python des applications autorisées dans Trousseaux d'accès (Access Control). — [même source](https://pypi.org/project/keyring/)
- Retour terrain (blog, 2026, **source unique**) : l'ACL Keychain est liée au binaire créateur ; un autre interpréteur Python (autre version) se voit refuser l'accès ; l'outil `security` en ligne de commande aurait été cassé pour les lectures sur macOS Tahoe, d'où la recommandation d'utiliser keyring. — [DEV Community](https://dev.to/euda1mon1a/macos-tahoe-broke-keychain-cli-reads-novel-findings-from-an-ai-agent-deployment-2p3o)
- Contrôle d'accès biométrique : flags `SecAccessControlCreateWithFlags` (`.userPresence`, `.biometryAny`, `.biometryCurrentSet`, `.devicePasscode`) ; ne s'appliquent au sens iOS que via la **data-protection keychain** (`kSecUseDataProtectionKeychain = true`) ; la keychain legacy (`login.keychain`) utilise des ACL par application. — [Apple, SecAccessControlCreateFlags](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags.md) ; [Apple, accessing keychain items with Face ID / Touch ID](https://developer.apple.com/documentation/localauthentication/accessing-keychain-items-with-face-id-or-touch-id.md)
- Retours développeurs : Touch ID exige une app signée avec entitlement ; un CLI non signé / ad hoc voit son `SecAccessControl` rejeté et doit prévoir un repli. — [Apple Developer Forums (684453)](https://developer.apple.com/forums/thread/684453) ; [crate tsafe-core (source Rust)](https://docs.rs/crate/tsafe-core/1.2.0/source/src/keyring_store/macos.rs)
- Outils « agent-aware » : **lkr (LLM Key Ring)** stocke les clés d'API LLM dans le Keychain et les injecte via `lkr exec -- python script.py` (« keys never in stdout ») ; **passkey-mcp** : secrets dans le keychain protégés par Touch ID / auth système, « AI assistants can list entries but never read values ». — [DEV, lkr](https://dev.to/yotta/stop-storing-llm-api-keys-in-plaintext-env-files-introducing-llm-key-ring-lkr-4mle) ; [GitHub passkey-mcp](https://github.com/thenicksanchez/passkey-mcp)
- Claude Code sandbox : règles `credentials.files` (`mode: deny` → lecture bloquée) et `credentials.envVars` (`deny` → variable retirée ; `mask` → le sous-processus reçoit une **valeur sentinelle** que le proxy remplace par la vraie valeur uniquement vers les hôtes `injectHosts`, ce qui exige `network.tlsTerminate`, expérimental). Par défaut le sandbox **laisse lire** `~/.ssh` et `~/.aws/credentials` sauf règle deny explicite. — [Claude Code, Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Docker Sandboxes : « credentials are injected at runtime and outside the MicroVM boundary, never baked into the environment ». — [Docker, Why MicroVMs (16 avr. 2026)](https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/)
- OpenJarvis : scanner de secrets / PII sur prompts et sorties, mode `block`. — [OpenJarvis security](https://open-jarvis.github.io/OpenJarvis/user-guide/security)

### Inferences
- Architecture recommandée : un **processus broker** (lancé par launchd, hors du processus LLM) est le seul à appeler `keyring.get_password`. L'agent ne manipule que des **handles** (`secret://gmail/oauth`) ; le broker résout le handle au moment de l'appel réseau (client HTTP côté broker, ou proxy qui substitue un sentinel comme le `mask` de Claude Code). Les résultats d'outils renvoyés au LLM passent par un redacteur (regex sur formats de clés + liste des valeurs connues).
- Si l'on veut une approbation biométrique « à la Touch ID » sans signer un binaire Python, la solution pratique est un petit helper Swift signé (ou l'app Trousseaux + retrait de Python de l'ACL pour forcer le prompt mot de passe à chaque lecture), plutôt que PyObjC sur Security.framework.
- Coffre chiffré applicatif (ex. fichier chiffré avec clé dérivée) : utile uniquement pour la portabilité ; la clé maîtresse devrait elle-même vivre dans le Keychain, sinon on ne fait que déplacer le problème. Le Keychain gagne pour l'intégration OS (chiffrement au repos, ACL par binaire, verrouillage de session).
- Le sandbox doit explicitement `denyRead` les chemins de credentials et `deny` les variables d'environnement sensibles ; les défauts (Claude Code) ne le font pas.

### Gaps
- Aucune source officielle Apple ou keyring décrivant précisément l'identification du binaire dans l'ACL (hash, chemin, signature) ; une seule source tierce.
- Pas d'exemple Python vérifié d'accès à la data-protection keychain avec `SecAccessControl` (la piste PyObjC / ctypes n'a pas été testée).

## Question 4 — Sandboxing de l'exécution de code sur macOS : sandbox-exec, Docker / OrbStack, Apple Containerization (macOS 26), sandboxes cloud type E2B ; allowlists réseau

### Takeaway
Trois niveaux coexistent fin 2026 : (1) **Seatbelt / sandbox-exec** — déprécié mais fonctionnel sur Tahoe, utilisé par Anthropic (`sandbox-runtime`) avec un proxy localhost comme unique sortie réseau ; (2) **micro-VM locales** — Apple `container` (une VM Linux par conteneur, macOS 26, Apple silicon) et Docker Sandboxes (`sbx`, Hypervisor.framework, daemon Docker privé, politique réseau) ; (3) **VM cloud à la demande** — E2B (allow/deny egress par domaine ou CIDR, pause/reprise). L'allowlist réseau se fait partout au niveau d'un proxy ou d'un firewall de VM, jamais en comptant sur le modèle.

### Cited Findings

**Seatbelt / sandbox-exec**
- Claude Code : « On macOS, sandboxing uses the built-in Seatbelt framework » ; rien à installer ; Linux/WSL2 → bubblewrap + socat (+ seccomp optionnel) ; Windows natif → non sandboxé. Désactivé par défaut ; activer via `/sandbox` ou `"sandbox": {"enabled": true}`. — [Claude Code, Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Réseau : « A sandboxed command has no direct route to the network » ; Seatbelt « blocks connections other than the one to the sandbox proxy » ; le proxy tourne hors sandbox et pose `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` ; les outils qui ignorent ces variables (`ssh`, drivers DB) ne peuvent pas se connecter ; UDP / QUIC / ICMP bloqués. Clés : `network.allowedDomains` (vide = aucun réseau), `deniedDomains` (prioritaire), `strictAllowlist` (deny silencieux au lieu de prompt), `allowManagedDomainsOnly`, `allowLocalBinding` (ouvre localhost, à éviter), `httpProxyPort`/`socksProxyPort`. Filesystem : `allowWrite`, `denyWrite`, `denyRead`, `allowRead` ; « Protected paths » toujours en deny-write (`.claude`, `.mcp.json`, rc shells, `.git/hooks`). `autoAllowBashIfSandboxed` par défaut `true` ; `excludedCommands` sort des commandes du sandbox ; `allowUnsandboxedCommands: false` interdit le repli ; `failIfUnavailable: true` arrête au démarrage si le sandbox ne peut pas tourner. Hooks, serveurs MCP locaux, LSP et `apiKeyHelper` tournent **hors** sandbox. — [même source](https://code.claude.com/docs/en/sandboxing)
- `sandbox-runtime` (srt, Anthropic, « Beta Research Preview », Apache 2.0) : « uses sandbox-exec with dynamically generated Seatbelt profiles » ; le profil n'autorise que le port localhost des proxies HTTP + SOCKS5 ; écritures refusées par défaut, lectures autorisées par défaut ; sockets Unix bloquées par défaut (contrôlées par chemin sur macOS) ; options dangereuses documentées : `enableWeakerNetworkIsolation` (exfiltration possible via `trustd`), `allowAppleEvents` (lancer d'autres apps hors sandbox), `allowLocalBinding`. Usage : `srt "curl example.com"`, `srt --settings cfg.json npm install`. — [README sandbox-runtime](https://cdn.jsdelivr.net/gh/anthropics/sandbox-runtime/README.md) ; [GitHub anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)
- Statut de dépréciation : plusieurs projets 2026 constatent que `sandbox-exec` reste fonctionnel sur Sequoia et Tahoe sans remplacement Apple pour un usage CLI ; un fil openssh-unix-dev (août 2026) cite la page `sandbox_init(3)` indiquant que les profils sont dépréciés et ne doivent pas être utilisés en compilant contre SDK ≥ 27.0 — **extrait de seconde main, non confirmé** sur la doc Apple. — [openssh-unix-dev, août 2026](https://lists.mindrot.org/pipermail/openssh-unix-dev/2026-August/042691.html) ; [gastown.dev, macOS sandbox-exec](https://gastown.dev/docs/research/macos-sandbox-exec)
- Risque des profils « allow default » : Pillar Security a documenté une évasion du sandbox Seatbelt d'Antigravity (Google) construit en mode « allow par défaut ». — [Pillar Security](https://www.pillar.security/blog/escaping-antigravitys-allow-default-seatbelt)

**Apple Containerization / `container` (macOS 26)**
- Framework : « Containerization executes each Linux container inside of its own lightweight virtual machine » ; « Uses Apple's `Virtualization` framework directly; no extra binaries required » ; `vminitd` est le premier processus de la VM et expose une API gRPC via vsock ; noyau Linux requis (config optimisée fournie, testé à partir de 6.14.9, VIRTIO compilé en dur) ; build : Apple silicon + macOS 26 + Xcode 26, « Older versions of macOS are not supported » ; IP dédiée possible par conteneur. — [README apple/containerization](https://raw.githubusercontent.com/apple/containerization/main/README.md)
- CLI `container` : images OCI, Swift, Apple silicon obligatoire, macOS 26 seule version supportée ; versions « produit » (pas semver) ; sous-commande `cluster` expérimentale ; pas de section sécurité ni de garantie d'isolation explicite dans le README. — [README apple/container](https://raw.githubusercontent.com/apple/container/main/README.md)
- Presse : annoncé WWDC 2025 ; réseaux isolés sur macOS 26 (conteneurs sur réseaux différents ne se joignent pas) ; Compose non supporté ; un article (opensourceforu, juin 2026) parle d'une « 1.0 » le 9 juin 2026 — **non recoupé** avec les releases GitHub. — [InfoQ (juin 2025)](https://www.infoq.com/news/2025/06/apple-container-linux) ; [opensourceforu (2026)](https://www.opensourceforu.com/2026/06/apple-launches-container-to-run-linux-containers-inside-micro-vms-on-mac/)

**Docker Sandboxes (`sbx`)**
- MicroVM par session d'agent avec son propre noyau, daemon Docker privé, « no path back to the host » ; VMM maison sur **Hypervisor.framework** (macOS), WHP (Windows), KVM (Linux) ; Firecracker écarté faute de support macOS/Windows ; « An LLM deciding its own security boundaries is not a security model » ; politique réseau (endpoints autorisés) définie avant l'exécution ; install `brew install docker/tap/sbx` ; billet du 16 avr. 2026. — [Docker, Why MicroVMs](https://www.docker.com/blog/why-microvms-the-architecture-behind-docker-sandboxes/)
- Docs : local (gratuit, y compris usage commercial) ou cloud (pay-as-you-go) ; politiques réseau séparées local / cloud ; gestion centralisée des politiques en abonnement payant. — [Docker docs, Sandboxes](https://docs.docker.com/ai/sandboxes/)
- Annonce initiale (jan. 2026) : microVM pour macOS (Apple silicon) et Windows ; seul le répertoire projet est partagé avec l'hôte ; agents supportés : Claude Code, Codex, Copilot, Cursor. — [Docker blog, Docker Sandboxes](https://www.docker.com/blog/docker-sandboxes-run-claude-code-and-other-coding-agents-unsupervised-but-safely/)

**E2B (sandboxes cloud)**
- « E2B provides isolated sandboxes that let agents safely execute code » ; « A fast, secure Linux VM created on demand… which you can pause and resume » (pause = snapshot FS + mémoire) ; `pip install e2b` ; `Sandbox.create()` puis `sandbox.commands.run(...)` ; nécessite `E2B_API_KEY`. — [docs.e2b.dev](https://docs.e2b.dev/)
- Réseau : accès Internet sortant **par défaut** ; `allow_internet_access=False` ≡ `deny_out=['0.0.0.0/0']` ; `allow_out` / `deny_out` acceptent IP, CIDR, domaines (domaines seulement en allow, et il faut alors tout refuser dans deny) ; wildcards `*.domaine` ; filtrage par domaine limité à HTTP 80 / TLS 443 (QUIC non supporté) ; `8.8.8.8` auto-autorisé si un domaine est en allow, `dns_servers` configurable ; allow prime sur deny ; `update_network` remplace la config. Piège : une connexion TCP bloquée peut sembler réussir (le firewall accepte avant de décider). — [E2B, internet access](https://docs.e2b.dev/sandbox/internet-access)
- Durée : 24 h max en continu (Pro), 1 h (Hobby) ; pause/reprise pour aller au-delà. — [E2B, lifecycle](https://docs.e2b.dev/sandbox/lifecycle)
- Technologie d'isolation : les pages lues ne nomment plus Firecracker ; mon information antérieure (E2B sur Firecracker microVMs) est **ancienne et non reconfirmée** ici.

**OrbStack**
- Machines isolées : par défaut une machine « isolated » ne joint pas l'hôte macOS mais joint encore les autres machines OrbStack et Internet ; `--isolate-network` bloque aussi les autres machines et les IP de l'hôte, en gardant Internet. — [OrbStack docs, isolated machines](https://docs.orbstack.dev/machines/isolated)
- Projet tiers qui l'utilise pour des agents : `--isolate-network` ne couvre pas le LAN physique (ajout de règles nftables et retrait de sudo dans la VM) ; les conteneurs OrbStack partagent un noyau, donc ne conviennent pas à du code qui tente activement une évasion. — [GitHub PhaseSoftware/sandbox](https://github.com/phasesoftware/sandbox)

**E2B — isolation (complément)**
- Page entreprise E2B (revendication vendeur) : une microVM par session avec noyau invité séparé sur KVM ; un exploit noyau dans la sandbox doit encore s'évader de Firecracker. Repris par Dreadnode, qui fait tourner ses sandboxes hébergées dans des microVM Firecracker E2B. — [E2B enterprise](https://e2b.dev/enterprise.md) ; [Dreadnode docs](https://docs.dreadnode.io/sandboxes/isolation/)

### Inferences
- Pour un agent always-on sur un Mac personnel, la hiérarchie pratique est : **Seatbelt + proxy** pour les commandes shell courantes (latence nulle, accès au FS hôte contrôlé par allowWrite/denyRead), **micro-VM** (Apple `container` ou Docker `sbx`) pour tout code non fiable, installation de paquets ou tâche longue autonome, et **E2B** seulement si l'on accepte une dépendance cloud (utile pour isoler totalement du Mac, mais la trifecta reste : données envoyées hors machine).
- Réutiliser directement `sandbox-runtime` (srt) comme bibliothèque / CLI depuis Python (`subprocess.run(["srt", "--settings", cfg, cmd])`) est la voie la plus courte pour obtenir un Seatbelt « deny-by-default » avec allowlist de domaines, en acceptant son statut beta et la dépréciation d'Apple ; prévoir une bascule vers `container` si Apple retire `sandbox_init` des SDK futurs.
- Règles réseau minimales pour Friday : allowlist explicite (API LLM, IMAP/SMTP du fournisseur, pont domotique en LAN), `strictAllowlist` équivalent (deny silencieux + journal), pas de `allowLocalBinding` (sinon le sandbox atteint les services localhost : Home Assistant, bases, serveurs MCP), DNS filtré (E2B le gère ; côté Seatbelt le proxy résout lui-même).
- Les serveurs MCP locaux et hooks tournent hors sandbox dans Claude Code : pour Friday, tout connecteur (e-mail, domotique) doit être lui-même lancé **dans** un sandbox ou en processus séparé à privilèges réduits.
- Le fait que les défauts (lecture de `~/.ssh` autorisée, Internet ouvert chez E2B, `autoAllowBashIfSandboxed: true`) soient permissifs est une leçon : la configuration doit être « fail-closed » et vérifiée par un test de non-régression (tenter de lire un secret / joindre un domaine interdit au démarrage).

### Gaps
- Pas de source primaire Apple sur les garanties de sécurité de Containerization (le README n'a pas de section sécurité) ni sur le calendrier de retrait de `sandbox-exec`.
- OrbStack : seule la page « isolated machines » et un projet tiers ont été trouvés ; pas de modèle de menace officiel. Avec un noyau partagé et un LAN joignable par défaut, c'est une frontière plus faible qu'Apple `container` ou Docker `sbx`, et la machine isolée laisse quand même atteindre le pont domotique en LAN.
- E2B : Firecracker n'est confirmé que par la page entreprise d'E2B et des tiers, pas par la doc technique ; le timeout par défaut n'est pas confirmé.

## Question 5 — Journalisation d'audit pour agents : logs structurés, OpenTelemetry pour apps LLM, SQLite WAL

### Takeaway
Fin 2026 la pile « raisonnable » est : logs structurés JSON (structlog) avec contexte lié (session / run / tool_call id) et **redaction** avant sortie ; traces OpenTelemetry suivant les conventions GenAI (`invoke_agent`, `execute_tool`, `chat`), encore au statut **Development** (noms d'attributs instables, versions à épingler) ; et une table d'audit **SQLite en mode WAL** append-only (triggers anti UPDATE/DELETE + chaînage de hachés) pour l'historique « ce qui a été montré vs exécuté » exigé par OWASP ASI09.

### Cited Findings
- OWASP ASI09 : « keep immutable logs of what was displayed versus what ran » ; confirmations montrant l'action brute. — [Cycode, résumé OWASP](https://cycode.com/blog/owasp-top-10-agentic-applications/)
- OTel GenAI : conventions `gen_ai.*` au statut Development (« names can change between releases without a deprecation window ») ; le 12 juin 2026 (v1.42.0) elles ont quitté le dépôt principal pour `open-telemetry/semantic-conventions-genai` (avec MCP) ; pas de release taguée, schéma « TODO » ; spans `chat {model}`, `invoke_agent {agent}`, `execute_tool {tool}` ; attributs requis `gen_ai.operation.name`, `gen_ai.provider.name` ; `gen_ai.agent.name`, `gen_ai.tool.name` ; contenu des prompts dans l'événement `gen_ai.client.inference.operation.details`, **opt-in** (`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` donné en exemple, comportement variable selon la lib). — [Dash0, OTel GenAI conventions (sept. 2026)](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained) ; [GitHub semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)
- Conseil répété : épingler les versions d'instrumentation tant que la spec bouge ; les conventions « chat/embeddings » sont mûres, « agent / tool orchestration » toujours en Development. — [OpenObserve guide](https://openobserve.ai/blog/opentelemetry-genai-semantic-conventions/) ; [Greptime (mai 2026)](https://www.greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)
- Une source (Business Tech Navigator, juin 2026) affirme une « spec stable » : contredite par les sources détaillées, **à ignorer**. — [businesstechnavigator](https://businesstechnavigator.com/news/opentelemetry-genai-semantic-conventions-agents-2026)
- structlog : en production émettre du JSON ; `JSONRenderer` en fin de chaîne de processeurs ; logger « bound » qui porte un contexte (session/run id) réinjecté dans chaque entrée ; merge de contextvars pour l'async. — [structlog, Logging best practices](https://www.structlog.org/en/stable/logging-best-practices.html)
- SQLite WAL : doc officielle — WAL ne fonctionne pas sur un système de fichiers réseau ; lecteurs non bloqués par l'écrivain. — [sqlite.org/wal](https://www.sqlite.org/wal.html)
- Pattern audit SQLite (ADR d'un projet d'agent) : SQLite + WAL choisi pour zéro dépendance (stdlib Python), latence d'écriture sub-ms (claim de l'auteur) ; triggers qui avortent UPDATE/DELETE sur la table d'événements ; chaînage de hachés entre entrées pour détecter la falsification ; copie à chaud avec `cp` peut manquer le contenu du WAL → utiliser l'API backup. — [Harombe ADR 004](https://smallthinkingmachines.github.io/harombe/decisions/004-sqlite-audit-logging) ; [Fly.io, SQLite internals WAL](https://fly.io/blog/sqlite-internals-wal/)
- Claude Code journalise ce que le classificateur a bloqué et pourquoi (ex. `[Data Exfiltration]`), ce qui illustre l'intérêt de tracer la **raison** d'un refus. — [Claude Code, Permission modes](https://code.claude.com/docs/en/permission-modes)
- Coding agents émettant déjà des traces OTel GenAI (Copilot, Codex, Claude Code en beta) — cité via blog OTel par Dash0 / OpenObserve. — [Dash0](https://www.dash0.com/knowledge/opentelemetry-genai-semantic-conventions-explained)

### Inferences
- Schéma d'événement minimal pour Friday (JSON + SQLite) : `ts`, `session_id`, `run_id`, `step`, `kind` (llm_call / tool_call / approval / denial / sandbox_violation), `tool`, `args_redacted`, `args_hash`, `taint_sources`, `decision` (allow/ask/deny + règle ou raison), `shown_to_user` (texte exact affiché), `executed` (commande/payload exact), `result_hash`, `prev_hash`. Les triggers `BEFORE UPDATE/DELETE … RAISE(ABORT)` + `PRAGMA journal_mode=WAL` + `synchronous=NORMAL` donnent un journal local robuste sans serveur.
- Ne jamais stocker les valeurs de secrets ni le contenu complet des e-mails par défaut dans les logs ; activer la capture de contenu OTel seulement en débogage (opt-in), et faire passer tous les processeurs par un redacteur avant `JSONRenderer`.
- Utiliser les noms de spans OTel (`invoke_agent`, `execute_tool`) même sans collecteur : cela structure le code et permet un export ultérieur, mais isoler les noms d'attributs dans un module unique pour absorber les renommages.
- Journaliser les **violations de sandbox** (connexion refusée par le proxy, écriture refusée) comme signaux de détection d'injection : c'est l'indicateur le plus fiable qu'une instruction hostile a tenté d'agir.

### Gaps
- Aucune source faisant autorité sur la conception d'une piste d'audit spécifique aux agents (rétention, quoi logger des arguments vs résultats) ; les pratiques ci-dessus sont assemblées à partir de docs générales et de projets individuels.
- Pas de nom de package Python d'instrumentation OTel GenAI confirmé dans les pages lues (OpenLLMetry / Traceloop mentionné sans version).
