# Pipeline vocal basse latence pour un assistant personnel local sur macOS (Apple Silicon) — état de l'art novembre 2026

Objectif : 800 ms de « time-to-first-audio » bout en bout (fin de parole utilisateur → premier échantillon audio de la réponse). Cible : macOS Apple Silicon, Python 3.11+. Tout ce qui exige CUDA/pynvml est signalé comme non applicable.

Note méthodologique : la plupart des chiffres de latence sont auto-déclarés par les éditeurs ou issus d'un seul banc d'essai. Les quelques mesures indépendantes (Humanness Index de Vapi, leaderboard Coval, mac-whisper-speedtest) sont signalées comme telles. Les données antérieures à 2026 sont datées.

## 1. Wake word : openWakeWord vs Picovoice Porcupine vs alternatives sur macOS ; entraînement d'un mot-clé custom (« Hey Friday ») ; coût CPU

### Takeaway
Porcupine n'est plus un choix viable pour un projet personnel : Picovoice a annoncé la fin de son offre gratuite au 30 juin 2026 et la désactivation des AccessKeys (le SDK ne démarre pas sans clé valide, même hors ligne). Les deux options locales crédibles sont openWakeWord (Apache 2.0, mais modèles pré-entraînés CC BY-NC-SA, macOS non listé officiellement) et surtout **livekit-wakeword v2** (Apache 2.0, Python 3.11+, macOS/Swift supporté, entraînement d'un mot-clé custom en ~1 h sur un Mac M4 Pro, ~1 ms par pas de 80 ms sur un seul cœur CPU).

### Cited Findings
- openWakeWord : code sous Apache 2.0, mais les modèles pré-entraînés sont sous CC BY-NC-SA 4.0 (données d'entraînement à licence incertaine) — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- openWakeWord : traitement par trames de 80 ms ; un seul cœur de Raspberry Pi 3 fait tourner 15–20 modèles simultanément en temps réel ; cibles de qualité : < 0,5 fausse acceptation/heure et < 5 % de faux rejets (corpus Dinner Party, 5,5 h) — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- openWakeWord : plateformes documentées = Linux (onnxruntime + tflite-runtime) et Windows (onnxruntime seulement) ; macOS n'est pas mentionné ; dernière version documentée v0.6.0 (11/02/2024, donc ancienne) — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- openWakeWord : entraînement custom via notebook Google Colab « en < 1 h », données synthétiques générées par TTS open source, « plusieurs milliers » d'exemples minimum recommandés, ~30 000 h de données négatives utilisées pour les modèles fournis — [openWakeWord README](https://github.com/dscripka/openWakeWord)
- openWakeWord : par défaut `ncpu=1`, device `cpu` ou `gpu` ; aucun benchmark CPU Apple Silicon trouvé — [recherche web openWakeWord macOS](https://github.com/cnhup/openWakeWord)
- onnxruntime officiel fournit désormais des binaires arm64 macOS avec CoreML EP ; le wheel tiers onnxruntime-silicon n'est plus nécessaire — [onnxruntime-silicon (archivé)](https://github.com/cansik/onnxruntime-silicon)
- Le fallback CoreML → CPU d'onnxruntime est silencieux par défaut (pas d'avertissement) — [theneuralbase CoreMLExecutionProvider](https://theneuralbase.com/onnx/learn/intermediate/coremlexecutionprovider-mac/)
- Picovoice : le Free Tier est supprimé le 30 juin 2026, les AccessKeys gratuites sont désactivées, « le SDK ne fonctionne pas sans clé valide », la clé est vérifiée au démarrage du moteur (donc les déploiements hors ligne sont touchés) ; Picovoice se concentre sur l'entreprise et n'a pas de niveau non-commercial prévu — [Home Assistant Community, compte rendu d'un e-mail Picovoice](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744)
- Picovoice : la page pricing officielle décrit un « Developer Plan » (jusqu'à 1 000 h/mois ou 100 utilisateurs/mois selon les moteurs) sans afficher de prix ; des sites tiers citent 899 $/mois ou 30 000 $/an entreprise, non fiables — [picovoice.ai/pricing](https://picovoice.ai/pricing) ; [softwareadvice](https://www.softwareadvice.com/speech-recognition/picovoice-profile)
- Un utilisateur HA rapporte que Porcupine reste nettement plus fiable qu'openWakeWord pour un mot-clé custom en japonais ; un autre estime l'entraînement openWakeWord custom (Piper pour les clips synthétiques + ~4 Go de données de fond) à 1–2 h, le réglage du seuil étant l'étape clé — [Home Assistant Community](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744)
- livekit-wakeword v2.1.2 (11 nov. 2026) : Apache-2.0, Python 3.11+ ; modèle Standard ONNX ~7 Mo (Python, Swift iOS/macOS, JS), modèle Micro int8 TFLite 451 Ko (ESP32) ; l'ancienne implémentation basée sur openWakeWord est dépréciée et ses modèles incompatibles — [PyPI livekit-wakeword](https://pypi.org/project/livekit-wakeword/)
- livekit-wakeword : entraînement custom nécessite un GPU CUDA **ou un Mac Apple Silicon**, `uv`, et un projet LiveKit Cloud (plan gratuit) pour la génération TTS des exemples ; pipeline `setup → train → eval → listen` ; ~11 min sur GPU datacenter, **~59 min sur Mac M4 Pro** ; phrases multilingues via `--language`, hard negatives, prononciations ARPAbet — [PyPI livekit-wakeword](https://pypi.org/project/livekit-wakeword/)
- livekit-wakeword : coût CPU ~1 ms par pas de 80 ms sur un thread ; benchmark éditeur : 16,5 ms CPU par seconde d'audio contre 30,5 ms (nanowakeword) et 29,5 ms (openWakeWord) — [PyPI livekit-wakeword](https://pypi.org/project/livekit-wakeword/) (chiffres du vendeur)
- ViolaWake (projet concurrent open source) revendique EER 5,49 % vs 8,24 % pour openWakeWord — chiffre du concurrent, non indépendant — [ViolaWake blog](https://violawake.pages.dev/blog/open-source-vs-proprietary-wake-word-detection-2026)
- Sur Apple, aucune API OS de wake word custom pour les apps tierces : il faut une capture micro permanente, ce qui allume l'indicateur micro orange/rouge dans la barre de menus — [Picovoice blog iOS](https://picovoice.ai/blog/ios-speech-recognition/)

### Inferences
- Pour « Hey Friday » : livekit-wakeword est le meilleur compromis 2026 (licence Apache, macOS supporté explicitement, entraînement local sur le Mac en ~1 h, charge CPU négligeable ~2 % d'un cœur). Le seul irritant : la génération des exemples TTS passe par LiveKit Cloud (compte gratuit) — pas totalement hors ligne pour l'entraînement, mais l'inférence est 100 % locale.
- openWakeWord reste utilisable sur macOS via onnxruntime (arm64 natif), mais sans support officiel, avec un dépôt peu actif depuis 2024 et des modèles pré-entraînés non commerciaux ; à réserver comme solution de repli.
- Budget latence : la détection du wake word est hors du chemin critique des 800 ms (elle précède la parole), mais sa trame de 80 ms + le pas de VAD fixent le « temps de réveil » ressenti (~100–200 ms).

### Gaps
- Aucune mesure publiée de la charge CPU d'openWakeWord ou de livekit-wakeword spécifiquement sur Apple Silicon (M-series) ; les chiffres sont RPi/x86 ou vendeur.
- Prix actuel du Developer Plan Picovoice introuvable sur la page officielle (page vide au fetch).
- Aucun test comparatif indépendant de taux de faux réveils entre livekit-wakeword, openWakeWord et Porcupine en 2026.

## 2. VAD : Silero VAD version courante, seuils, alternatives

### Takeaway
Silero VAD v6 (sortie 26 août 2026, v6.2.3 au 23 sept.) est le standard de fait, MIT, ~1,2–2 Mo, < 1 ms par chunk de 32 ms sur un thread CPU (0,75 ms mesuré sur M1 Max, ~0,17 ms sur M5 Max en port MLX). Seuil par défaut 0,5 dans la plupart des intégrations ; Pipecat utilise 0,7 avec `start_secs`/`stop_secs` = 0,2 s. Alternatives : TEN VAD (drop-in dans Pipecat), port MLX/CoreML (FluidAudio) pour l'ANE.

### Cited Findings
- Silero VAD : licence MIT, modèle JIT ~2 Mo, « un chunk audio (30+ ms) prend < 1 ms sur un seul thread CPU », 8 kHz et 16 kHz, entraîné sur > 6 000 langues ; dépendance obligatoire `torch>=1.12`, extras `onnxruntime>=1.16.1` — [silero-vad README](https://github.com/snakers4/silero-vad)
- Silero VAD v6.0 (26 août) : −16 % d'erreurs sur données réelles bruitées, −11 % en validation multi-domaine, nouvel algorithme d'entraînement, comparaison ajoutée vs TEN VAD, points faibles connus : musique avec instruments « voix », voix très aiguës (enfants, cartoons) ; timestamps en secondes, `drop_chunks`, suppression de `hop_size_ratio`, source C++ libtorch — [silero-vad releases](https://github.com/snakers4/silero-vad/releases)
- v6.2 (6 nov.) : paradigme d'entraînement retravaillé, meilleure stabilité hors distribution (voix d'enfants, voix étouffées, appels téléphoniques de basse qualité) ; v6.2.1 : onnxruntime devient optionnel ; v6.2.2 : chemin ONNX « sequence » 16 kHz offline ; v6.2.3 (23 sept.) : torchaudio optionnel, seul torch requis — [silero-vad releases](https://github.com/snakers4/silero-vad/releases) (années non affichées sur la page ; v6.0 = août 2025 ou 2026 selon la chronologie, à vérifier)
- Port MLX silero-vad-v6 : ~309 K paramètres, F32, ~1,2 Mo ; chunk de 512 échantillons (32 ms @16 kHz) + 64 échantillons de contexte ; v6 ne livre que la branche 16 kHz ; p50 par chunk **0,75 ms sur M1 Max (MLX CPU, mx.compile)**, 1,46 ms sur GPU MLX sans compile, **~0,17 ms sur M5 Max** — [mlx-community/silero-vad-v6](https://huggingface.co/mlx-community/silero-vad-v6)
- F1 trame par trame (réunion anglaise 44 min) : v6 0,8656 @0,30 → 0,8534 @0,60 ; v5 marginalement supérieur (+0,003) à chaque seuil, « équivalents au bruit de mesure près » — [mlx-community/silero-vad-v6](https://huggingface.co/mlx-community/silero-vad-v6)
- Seuil par défaut 0,5 (confiance 0–1) dans NeMo Curator et dans le crate Rust `silero` — [NVIDIA NeMo Curator](https://docs.nvidia.com/nemo/curator/v26.07/curate-audio/process-data/quality-filtering/vad.md) ; [docs.rs silero](https://docs.rs/crate/silero/0.1.1/source/src/options.rs)
- Pipecat `SileroVADAnalyzer` / `VADParams` par défaut : `confidence=0.7`, `start_secs=0.2`, `stop_secs=0.2`, `min_volume=0.6` ; 8 kHz (256 échantillons/trame) ou 16 kHz (512) ; inférence CPU via ONNX runtime, état conservé sur tout le flux — [docs Pipecat SileroVADAnalyzer](https://docs.pipecat.ai/server/utilities/audio/silero-vad-analyzer)
- LiveKit Agents : le détecteur de tour exige `min_silence_duration ≥ 0,25 s` ; la valeur par défaut Silero dans LiveKit est 0,55 s — [LiveKit turn-detector docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- FluidAudio (CoreML, Swift) utilise un seuil 0,75 dans son exemple et teste 0,3 dans son benchmark — [FluidAudio VAD docs](https://docs.fluidinference.com/vad/getting-started.md)
- TEN VAD : analyseur communautaire « drop-in » remplaçant SileroVADAnalyzer dans Pipecat — [docs Pipecat TEN VAD](https://docs.pipecat.ai/api-reference/server/services/vad/ten-vad)

### Inferences
- Coût VAD sur Apple Silicon : ~0,2–1 ms par chunk de 32 ms → < 3 % d'un cœur ; négligeable dans le budget 800 ms. Le vrai coût du VAD est le **délai de fin de parole** (`stop_secs` / `min_silence_duration`) : 200 ms (Pipecat) à 550 ms (LiveKit) viennent se soustraire directement au budget. Un endpointing sémantique (Smart Turn, cf. §5) permet de réduire ce délai sans multiplier les coupures.
- Recommandation pratique : silero-vad v6 via `onnxruntime` (sans torch pour alléger) ou le port MLX ; seuil de départ 0,5, à monter vers 0,6–0,7 en environnement bruité ; `min_silence` ~250–300 ms + endpointing sémantique.

### Gaps
- Les paramètres par défaut upstream (`threshold`, `min_silence_duration_ms`, `speech_pad_ms`) ne sont pas affichés dans le README fetché ; seules les intégrations (Pipecat, LiveKit, NeMo) les documentent.
- Pas de comparaison indépendante TEN VAD vs Silero v6 en 2026 (Silero publie sa propre comparaison).
- Les années des releases Silero ne sont pas affichées sur la page GitHub ; chronologie v6.0 → v6.2.3 reconstituée par ordre.

## 3. STT : Whisper large-v3 vs faster-whisper vs whisper.cpp vs MLX-whisper sur Apple Silicon ; cloud streaming (Deepgram, AssemblyAI, OpenAI) ; transcriptions partielles

### Takeaway
Sur Apple Silicon, **faster-whisper (CTranslate2) est CPU-only, sans backend Metal** et ~7× plus lent que mlx-whisper : non recommandé. mlx-whisper large-v3-turbo transcrit une phrase courte en ~1,0 s sur M4 ; whisper.cpp (CoreML + q5_0) ~1,2 s ; mais **Parakeet TDT 0.6B v2 (parakeet-mlx ~0,5 s, FluidAudio CoreML ~0,19 s)** est 2–5× plus rapide. Pour du vrai streaming partiel local : WhisperKit (LocalAgreement, ~0,45 s de latence d'hypothèse sur M3 Max) ou Parakeet. En cloud, Deepgram Nova-3/Flux (~86–100 ms moyen jusqu'au transcript final après fin de parole, mesure indépendante Coval) reste la référence latence ; AssemblyAI Universal-3 Pro annonce P50 ~150 ms ; OpenAI GPT-Realtime-Whisper ~557 ms.

### Cited Findings — local Apple Silicon
- mac-whisper-speedtest (MacBook Pro M4 24 Go, phrase courte, temps moyen) : fluidaudio-coreml (parakeet-tdt-0.6b-v2) **0,19 s** ; parakeet-mlx **0,50 s** ; mlx-whisper large-v3-turbo **1,02 s** ; insanely-fast-whisper (MPS, 4-bit) 1,13 s ; whisper.cpp large-v3-turbo-q5_0 + CoreML, 4 threads **1,23 s** ; lightning-whisper-mlx 1,82 s ; WhisperKit large-v3 2,22 s ; whisper-mps 5,37 s ; **faster-whisper large-v3-turbo CPU int8, 12 threads 6,96 s** ; README cite ~110× temps réel pour FluidAudio sur M4 Pro — [anvanvan/mac-whisper-speedtest](https://github.com/anvanvan/mac-whisper-speedtest)
- Bill Mill (janv. 2026, fichier long « I have a dream », 10 runs) : mlx_whisper large-v3-turbo 13,1 s ± 0,3 vs whisper.cpp ggml-large-v3-turbo 26,7 s ± 0,6 → mlx_whisper **2,03× plus rapide** (1,78× dans son test 2024) ; matériel non précisé, CoreML non mentionné — [notes.billmill.org](https://notes.billmill.org/dev_blog/2026/01/updated_my_mlx_whisper_vs._whisper.cpp_benchmark.html)
- faster-whisper n'a pas de backend Metal et tourne CPU-only sur Mac (~3× temps réel sur M5 Pro selon un guide secondaire) — [PromptQuorum (source secondaire)](https://www.promptquorum.com/power-local-llm/local-whisper-stt-comparison-2026)
- whisper.cpp avec CoreML exécute l'encodeur sur l'Apple Neural Engine, estimé ~3× plus rapide que Metal seul ; large-v3 ~10× temps réel sur M5 Pro Metal (guide secondaire, non reproductible) — [codersera (source secondaire)](https://codersera.com/blog/faster-whisper-vs-whisper-cpp-speech-to-text-2026/)
- WhisperKit (article arXiv 2025, M3 Max, Neural Engine) : latence moyenne par mot des **hypothèses partielles ~0,45 s** (à égalité avec Fireworks, mieux que Deepgram 0,83 s) ; texte **confirmé ~1,7 s** pour tous les systèmes ; encodeur audio 612 ms → 218 ms (variante d750) ; décodeur 4,6 ms/passe sur ANE M3, 0,3 W ; large-v3-turbo 1,6 Go FP16 → 0,6 Go compressé ; WER 2,2 % sur le benchmark streaming ; deux flux : texte confirmé (stable) et hypothèse (révisable) via politique LocalAgreement — [arXiv 2507.10860](https://arxiv.org/html/2507.10860v1) (données 2025)
- Whisper-Streaming (LocalAgreement) ne « commit » un mot que si deux passes consécutives sont d'accord ; la queue non confirmée reste partielle — [Fora Soft streaming ASR 2026](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/streaming-asr-deepgram-whisper-assemblyai-2026)
- Parakeet TDT décrit comme le seul backend du projet HF speech-to-speech supportant la transcription progressive live ; Parakeet EOU (120 M, streaming) tourne sur CoreML/ANE — [instagit HF speech-to-speech](https://instagit.com/huggingface/speech-to-speech/live-transcription-parakeet-tdt-apple-silicon-performance.md)
- mlx-audio (MIT, Python 3.10+, Apple Silicon requis) supporte en STT : Whisper, Distil-Whisper, Qwen3-ASR, Parakeet (mode streaming), Voxtral Realtime (4B streaming), Nemotron Speech Streaming, Moonshine, Canary, etc. ; serveur REST compatible OpenAI (`/v1/audio/transcriptions`) ; aucun chiffre de latence publié — [Blaizzy/mlx-audio](https://github.com/Blaizzy/mlx-audio)
- Moonshine v2 : encodeur dont la latence est largement indépendante de la longueur de l'énoncé (adapté aux hypothèses partielles) ; WhisperKit note une perte de précision de Moonshine sur l'audio long — [arXiv 2602.12241](https://arxiv.org/pdf/2602.12241) ; [arXiv 2507.10860](https://arxiv.org/html/2507.10860v1)
- Apple SpeechAnalyzer (API macOS 26) émet des résultats partiels « volatiles » — [Eden AI guide dictée macOS](https://www.edenai.co/post/yap-whisper-and-cloud-stt-choosing-a-voice-dictation-stack-for-macos-apps)

### Cited Findings — cloud streaming
- Leaderboard Coval (30 jours au 28 oct. 2026, 897 tours de parole spontanés issus des données ouvertes Pipecat, latence = de la fin de parole détectée par un VAD commun au transcript final, hors connexion) : Deepgram Nova-3 WER 5,2 % / **86 ms** moyen ; Deepgram Flux WER 5,7 % / p50 **99 ms**, p95 165 ms ; Flux Multilingual 7,4 % / 99 ms ; AssemblyAI Universal Streaming 5,9 % (latence non classée) ; **OpenAI GPT Realtime Whisper WER 4,0 % / 557 ms** ; Speechmatics Linden 1 3,9 % / 272 ms ; Gladia Solaria 1 6,2 % / 436 ms ; Cartesia Ink 2 **3,4 % / 150 ms** — [Coval STT benchmarks 2026](https://www.coval.ai/blog/best-speech-to-text-providers-in-2026-independent-benchmarks-and-how-to-choose)
- Via Gradium (reprise Coval) : AssemblyAI Universal Streaming 57 ms plus lent que Nova-3 au P50, écart-type 237 ms — [Gradium STT benchmark 2026](https://gradium.ai/content/stt-api-benchmark-2026-latency-accuracy)
- AssemblyAI (auto-déclaré) : Universal-3 Pro Streaming P50 ~150 ms après détection de fin de parole par VAD, P90 ~240 ms ; WER 4,5 % vs Nova-3 6,66 % dans son propre benchmark juin 2026 — [AssemblyAI blog](https://assemblyai.com/blog/best-api-models-for-real-time-speech-recognition-and-transcription)
- Deepgram (auto-déclaré) : Nova-3 « sous 300 ms » côté serveur en temps réel — [Deepgram blog](https://deepgram.com/blog/deepgram-vs-assemblyai-vs-whisper)
- OpenAI Realtime API vise ~500 ms TTFB ; GPT-Realtime-Whisper lancé le 7 mai 2026 à 0,017 $/min — [CallSphere (source secondaire)](https://callsphere.ai/blog/tw26w19-gpt-realtime-whisper-streaming-stt-vs-deepgram)
- Tarifs Deepgram pay-as-you-go streaming : Nova-3 monolingue **0,0077 $/min**, multilingue 0,0092 $/min ; Flux EN 0,0077 $/min, Flux multilingue 0,0078 $/min ; pré-enregistré Nova-3 0,0043 $/min ; crédit gratuit 200 $ sans expiration (~43 000 min) — [deepgram.com/pricing](https://deepgram.com/pricing)
- Tarifs AssemblyAI streaming : Universal-3.6 Pro Realtime **0,45 $/h** (≈0,0075 $/min) ; Universal-Streaming EN ou multilingue 0,15 $/h (≈0,0025 $/min) ; facturation à la durée de session (temps idle compté) ; crédit gratuit 50 $ ; multilingue EN/ES/DE/FR documenté — [assemblyai.com/pricing](https://www.assemblyai.com/pricing)
- ElevenLabs Scribe v2 Realtime : ~150 ms de latence annoncée — [elevenlabs.io/pricing/api](https://elevenlabs.io/pricing/api)

### Inferences
- Pour le budget 800 ms en local : Whisper large-v3 (non-turbo) est à exclure ; même large-v3-turbo via MLX coûte ~1 s par énoncé court sur M4 en mode batch, soit tout le budget. Parakeet TDT 0.6B v2 (parakeet-mlx, ~0,5 s, ou FluidAudio CoreML ~0,19 s en Swift) est le seul chemin local qui laisse de la marge. Attention : Parakeet v2 est anglophone ; pour le français il faut Parakeet v3 multilingue (non benchmarké ici) ou Whisper turbo.
- La stratégie « STT en streaming pendant que l'utilisateur parle » (hypothèses partielles WhisperKit/Parakeet/Whisper-Streaming, ou Deepgram/AssemblyAI) ramène la latence STT perçue à la seule finalisation après fin de parole (~100–450 ms) au lieu de la transcription complète.
- Cloud : Deepgram Flux/Nova-3 (~100 ms) ou Cartesia Ink 2 (150 ms, meilleure WER) sont les seuls à laisser > 600 ms au LLM+TTS ; OpenAI Realtime Whisper (557 ms) consomme trop de budget.
- faster-whisper, insanely-fast-whisper et tout ce qui dépend de CUDA/pynvml : non applicable ou sous-optimal sur Apple Silicon.

### Gaps
- Aucun benchmark 2026 de Parakeet v3 multilingue (français) sur Apple Silicon.
- mac-whisper-speedtest ne mesure qu'une phrase, sans WER ; Bill Mill ne précise pas sa machine.
- Latence « premier token partiel » de mlx-whisper / whisper.cpp en mode streaming non publiée.
- Prix Cartesia Ink 2 et Speechmatics non collectés.

## 4. TTS : ElevenLabs Flash v2.5 (latence, prix), Qwen3-TTS, Kokoro, Orpheus, CosyVoice2, options locales Apple Silicon (latence premier chunk), contrôle d'émotion

### Takeaway
Cloud : ElevenLabs Flash v2.5 annonce ~100 ms (médiane modèle seul), mesuré indépendamment à **197 ms médian TTFB** (réseau inclus, Vapi Humanness Index juin 2026), à **0,04 $/1 000 caractères** en API ; les nouveaux modèles v4 Turbo (~100 ms, 90+ langues, audio tags) et v3 Conversational (~165 ms, audio tags) ajoutent le contrôle émotionnel. Cartesia Sonic 3.5 est plus rapide (128 ms). Local Apple Silicon : **Kokoro-82M (Apache-2.0)** est le seul modèle largement plus rapide que le temps réel sur CPU (RTF ~0,10 en ONNX) mais sans contrôle d'émotion ni français officiel ; **Qwen3-TTS 0.6B/1.7B (Apache-2.0, 10 langues dont le français, streaming « dès le premier caractère », 97 ms annoncés sur GPU)** tourne via mlx-audio avec un RTF ~0,5–0,65 sur M4 (donc faisable en streaming) et offre clonage + instructions de style ; Orpheus 3B est ~1,75× plus lent que le temps réel sur Mac (inutilisable en temps réel) ; CosyVoice2/3 n'a pas de port Apple Silicon documenté.

### Cited Findings — cloud
- ElevenLabs Flash v2.5 : ~100 ms médian « hors latence applicative et réseau », 32 langues, 40 000 caractères max, prix/caractère 50 % inférieur aux modèles Multilingual, recommandé pour les agents conversationnels ; Turbo v2.5 déprécié ; **v4 Turbo ~100 ms médian, 90+ langues, audio tags, recommandé pour les agents les plus expressifs** ; **v3 Conversational ~165 ms, 70+ langues, audio tags** ; Multilingual v2 (29 langues) et Eleven v3 (70+ langues, 5 000 car.) à latence plus élevée — [ElevenLabs models](https://elevenlabs.io/docs/overview/models)
- Mesure indépendante (Vapi Humanness Index, médiane de 50 appels streaming séquentiels, juin 2026, RTT réseau inclus) : Cartesia Sonic 3.5 **128 ms**, Sonic 2 159 ms, Sonic 3 166 ms, **ElevenLabs Flash v2.5 197 ms**, Turbo v2.5 265 ms, MiniMax Speech 2 Turbo 315 ms, Multilingual v2 1 006 ms — [Humanness Index Flash v2.5](https://humannessindex.vapi.ai/models/elevenlabs-flash-v2-5)
- ElevenLabs annonce 75 ms pour Flash à son lancement (déc. 2024) ; les tiers soulignent que c'est une mesure interne modèle seul — [The Decoder (déc. 2024)](https://the-decoder.com/elevenlabs-launches-flash-its-fastest-text-to-speech-ai-yet/) ; [okmiku](https://okmiku.com/blog/realtime-voice-agent-flash-vs-inworld-mini)

## 5. Barge-in / interruption ; frameworks packagés (Pipecat, LiveKit Agents, Vocode) et adéquation à une app desktop

### Takeaway
Le motif standard : VAD détecte la parole pendant la lecture TTS → `StartInterruptionFrame` (Pipecat) / interruption adaptative (LiveKit) → arrêt immédiat de la lecture audio et annulation du LLM/TTS en cours, puis filtres anti-faux-positifs (durée/mots minimum, timeout de fausse interruption avec reprise). Les deux frameworks embarquent désormais un détecteur de fin de tour sémantique local (Smart Turn v3.x ~8–11 Mo int8, 12–57 ms CPU, BSD-2 ; LiveKit v1-mini ~140–250 Mo, LiveKit Model License). **Pipecat (`LocalAudioTransport` PyAudio, BSD-2) est le plus adapté à une app desktop sans serveur** ; LiveKit Agents a un mode `console` local mais il est déprécié (v1.6.8) au profit de `lk agent console` et le framework suppose un serveur/room WebRTC ; Vocode (MIT) est en perte de vitesse (ralentissement constaté juillet 2026).

### Cited Findings
- Flux d'interruption standard : quand l'utilisateur parle pendant la réponse, le flux TTS s'arrête, la génération LLM est annulée, le STT reprend le nouvel audio ; « quand le barge-in se déclenche, l'audio TTS doit s'arrêter dans les 60 ms » — [FutureAGI barge-in 2026](https://futureagi.com/blog/voice-ai-barge-in-turn-taking-2026/) ; [AssemblyAI Vapi vs Pipecat vs LiveKit](https://assemblyai.com/blog/vapi-vs-pipecat-vs-livekit)
- Pipecat : le VAD émet `StartInterruptionFrame` au début de parole, ce qui déclenche l'interruption si activée ; les trames d'interruption sont envoyées hors bande pour traitement immédiat ; VAD par défaut `SileroVADAnalyzer` avec `stop_secs=0.2` + Smart Turn — [docs Pipecat speech input](https://docs.pipecat.ai/learn/speech-input) ; [docs Pipecat silero-vad processor](https://docs.pipecat.ai/api-reference/processors/audio/silero-vad)
- Pipecat `LocalAudioTransport` (PyAudio, périphériques par défaut ou `input_device_index`/`output_device_index`, `audio_in_enabled`, `audio_out_enabled`, `audio_out_10ms_chunks=4`, etc.) ; **pas de mention d'annulation d'écho** — [reference-server.pipecat.ai LocalAudioTransport](https://reference-server.pipecat.ai/en/stable/api/pipecat.transports.local.audio.html)
- Pipecat : les docs divergent sur l'emplacement du VAD (`TransportParams(vad_analyzer=…)` ancien vs `LLMUserAggregatorParams` nouveau) ; le haut-parleur local peut faire que le bot « s'entend » et s'interrompt — [recherche Pipecat LocalAudioTransport](https://docs.pipecat.ai/learn/speech-input)
- Pipecat v1.1.0 (27 avr. 2026) ; LiveKit Agents 1.5.9 (13 mai 2026) — [Fora Soft comparatif](https://www.forasoft.com/blog/article/pipecat-vs-livekit-agents)
- Smart Turn v3 (Daily/Pipecat) : backbone Whisper Tiny (39 M), 8 Mo, poids + données + script d'entraînement ouverts, BSD 2-Clause ; v3.1 int8 CPU **12 ms** (9 ms c7a.2xlarge, 37 ms c7a.medium, **57 ms c8g.medium ARM**) ; version par défaut embarquée `smart-turn-v3.2-cpu` ; conversions ONNX tierces : 33 Mo f32 / 11,1 Mo int8, ~36–37 ms — [daily.co Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/) ; [daily.co v3.1](https://www.daily.co/blog/improved-accuracy-in-smart-turn-v3-1/) ; [soniqo Smart-Turn-v3.2-ONNX](https://huggingface.co/soniqo/Smart-Turn-v3.2-ONNX) ; port CoreML tiers [aufklarer/Smart-Turn-v3.2-CoreML](https://huggingface.co/aufklarer/Smart-Turn-v3.2-CoreML)
- LiveKit Agents interruptions : `min_interruption_duration` (durée minimale de parole), `min_interruption_words` (nécessite STT), `false_interruption_timeout` (silence après interruption avant `agent_false_interruption`), `resume_false_interruption=True` reprend là où la réponse s'était arrêtée ; mode d'interruption adaptative par défaut sur LiveKit Cloud/dev, à activer explicitement en auto-hébergé — [LiveKit turns docs](https://docs.livekit.io/agents/build/turns/)
- LiveKit turn detector audio : `v1` servi sur LiveKit Inference, `v1-mini` local CPU (~140–250 Mo RAM), fallback automatique ; 14 langues dont le **français** ; prédictions > ~1 s → le tour est validé quand même ; endpointing `min_delay` 0,3 s / `max_delay` 2,5 s ; détecteur texte (Qwen2.5-0.5B, 396 Mo, 50–160 ms CPU) déprécié pour le SDK 2.0 ; licence « LiveKit Model License » — [LiveKit turn-detector docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- LiveKit mode console : `python myagent.py console` = I/O audio local sans serveur, `--list-devices`, `--input-device`, `--output-device`, `--text`, `--record` ; les modèles LiveKit Inference exigent quand même les variables `LIVEKIT_*` ; **release 1.6.8 : modes console et dev dépréciés au profit de `lk agent console`** (qui parle à l'agent via micro/haut-parleurs dans une « room simulée ») — [LiveKit AGENTS.md](https://cdn.jsdelivr.net/gh/livekit/agents@main/AGENTS.md) ; [releases.sh livekit-agents 1.6.8](https://releases.sh/release/rel_aiC_3tZmbYVr69q3uuJH-) ; [LiveKit CLI agent](https://docs.livekit.io/reference/developer-tools/livekit-cli/agent/)

- livekit-wakeword s'intègre comme plugin LiveKit Agents (docs « Wakeword detection ») — [LiveKit wakeword docs](https://docs.livekit.io/agents/multimodality/audio/wakeword.md)
- Vocode : MIT, dépôt vocodedev/vocode-python ; une revue de juillet 2026 note « des ralentissements potentiels de l'activité de développement » ; aucune archive confirmée — [Stork.ai Vocode](https://www.stork.ai/en/vocode) ; [tooldirectory juin 2026](https://tooldirectory.ai/tools/vocode-voice-ai-agents)
- Cekura publie des benchmarks d'orchestration barge-in (Retell, Vapi, Pipecat, LiveKit) mais aucun chiffre comparatif n'a pu être extrait — [Cekura barge-in](https://www.cekura.ai/discover/barge-in)

### Inferences
- Pour une app desktop macOS en Python : Pipecat + `LocalAudioTransport` + `SileroVADAnalyzer` + Smart Turn v3.2 CPU est la pile la plus directe et entièrement locale (BSD-2 / MIT / BSD-2). Un port CoreML tiers de Smart Turn existe pour viser l'ANE. Reste à gérer soi-même l'annulation d'écho (AEC) — sur macOS, l'AEC système via `kAudioUnitSubType_VoiceProcessingIO` ou l'usage d'un casque est le moyen d'éviter que le TTS ne déclenche le VAD/barge-in ; aucune des deux piles Python ne documente d'AEC desktop.
- LiveKit Agents reste utilisable localement (console / `lk agent console`) et offre les meilleurs garde-fous d'interruption (durée/mots min, reprise après fausse interruption), mais son architecture est pensée pour des rooms serveur ; plus de friction et de dépendances cloud (LiveKit Inference pour `v1`) pour un assistant personnel.
- Budget barge-in : VAD 32 ms + `start_secs` 200 ms (Pipecat) → ~230 ms avant déclenchement ; arrêt TTS visé < 60 ms ; `min_interruption_words` ≥ 1 ou `min_interruption_duration` ~0,3–0,5 s pour ignorer les « hmm » (back-channel).
- Budget 800 ms indicatif, local : fin de parole → VAD stop 200–300 ms + Smart Turn ~40–60 ms (ARM) → STT Parakeet-MLX finalisation ~100–300 ms (si streaming) → LLM premier token (hors périmètre, ~200–400 ms local) → TTS premier chunk Kokoro/Qwen3-TTS-MLX ~50–150 ms (estimation). Serré mais atteignable seulement avec STT et TTS en streaming et un endpointing agressif ; en cloud, Deepgram Flux (~100 ms) + ElevenLabs Flash/v4 Turbo (~200 ms) laissent ~400 ms au LLM.

### Gaps
- Aucun benchmark de latence barge-in (parole → arrêt audio) comparant Pipecat et LiveKit en 2026.
- Aucune documentation Pipecat/LiveKit sur l'annulation d'écho pour un transport micro/haut-parleur local sur macOS.
- Latence de Smart Turn v3.2 sur Apple Silicon (seuls des chiffres x86/Graviton ARM sont publiés).
- État exact du dépôt Vocode (archivé ou non, date du dernier commit) non vérifié directement sur GitHub.
