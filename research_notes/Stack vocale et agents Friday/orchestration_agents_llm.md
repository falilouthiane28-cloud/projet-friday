## Question 1 — Claude Agent SDK vs OpenAI Agents SDK vs LangGraph vs Pydantic AI vs CrewAI : handoffs, sous-agents, MCP, streaming, maturité

### Takeaway
Pour un orchestrateur « Conductor » Python qui route vers des agents spécialisés et qui doit exposer/consommer des outils MCP, deux candidats se détachent : le **Claude Agent SDK** (sous-agents natifs, MCP in-process via `@tool`, hooks, sessions, mais couplage total à Claude et à l'exécutable Claude Code) et **Pydantic AI** (typage fort, multi-fournisseur, MCP via FastMCP, « SubAgents » harness, 2.x très actif). L'OpenAI Agents SDK a le modèle de handoff le plus explicite (« handoffs are represented as tools ») mais est centré OpenAI ; LangGraph est un moteur de graphe durable (surdimensionné pour un assistant à 6 agents) ; CrewAI est orienté « équipes » et flows événementiels, avec un support MCP limité aux tools (pas de prompts/ressources).

**Recommandation** : Claude Agent SDK si Friday reste 100 % Claude et si l'on accepte le binaire Claude Code comme runtime (et la clause de licence : pas de login claude.ai pour les produits tiers) ; sinon Pydantic AI comme couche neutre avec handoff programmatique (le Conductor décide en code, pas seulement le LLM). Détails et justification dans les inférences.

### Cited Findings

**Claude Agent SDK (Python)**
- Le SDK « donne les mêmes outils, boucle d'agent et gestion de contexte que Claude Code, programmables en Python et TypeScript » ; c'est « une bibliothèque qui exécute le binaire Claude Code » — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Capacités listées : outils intégrés (Read/Write/Edit/Bash/web), hooks, sous-agents, MCP, permissions, sessions (reprise/fork), skills/commands/memory, plugins — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Contrainte de licence : « Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods » — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Sous-agents : définis par `AgentDefinition(description, prompt, tools, model, effort, mcpServers, maxTurns, background, permissionMode, ...)` passés via `ClaudeAgentOptions(agents={...})` ; Claude les invoque via l'outil `Agent` ; « context isolation » (seul le message final remonte au parent), « parallelization », restrictions d'outils par agent — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Par défaut un sous-agent s'exécute en arrière-plan (`status: "async_launched"`) et le rapport arrive à un tour ultérieur ; Claude attend quand il en a besoin ; `background=True` force l'arrière-plan — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Un sous-agent non-fork démarre avec un contexte vierge : il reçoit son propre system prompt + le prompt de l'outil Agent, pas l'historique du parent — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Limites configurables : profondeur `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (défaut 3), concurrence `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (défaut 20), budget `max_budget_usd` (sans limite par défaut) ; ces limites nécessitent Python SDK ≥ 0.2.127 — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Le champ `model` d'un sous-agent accepte les alias `'fable'`, `'opus'`, `'sonnet'`, `'haiku'`, `'inherit'` ou un ID complet — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- « Claude Opus 5 delegates to subagents more readily than earlier models », d'où l'importance des limites — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Sous-agents reprenables (`resume=session_id` + `agentId` extrait du résultat de l'outil Agent) ; transcripts stockés séparément — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Depuis Claude Code v2.1.210, le message final d'un sous-agent est scanné pour les motifs d'instruction (ex. `<system-reminder>`, `Human:`) et neutralisé avant lecture par le parent — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Le Python SDK n'a pas les champs `autoCompactWindow` ni `omitClaudeMd` (TypeScript seulement) ; l'outil `Workflow` (orchestration de dizaines à centaines d'agents hors contexte) est « available in the TypeScript Agent SDK v0.3.149 and later » — pas mentionné pour Python — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- MCP : serveurs stdio (`command`/`args`), HTTP (`"type": "http"`), SSE (`"type": "sse"`), ou serveurs « SDK MCP » in-process ; outils nommés `mcp__<server>__<tool>` ; permission obligatoire via `allowed_tools` (wildcard `mcp__server__*`) ; « Prefer `allowedTools` over permission modes for MCP access » — [Connect to external tools with MCP](https://code.claude.com/docs/en/agent-sdk/mcp.md)
- Timeout de connexion MCP 30 s par défaut (`MCP_TIMEOUT`), statut par serveur dans le message `system/init` (`pending`, `connected`, `failed`, `needs-auth`, `disabled`) ; le SDK « doesn't open a browser or run an interactive OAuth flow » : on passe le token dans `headers` — [Connect to external tools with MCP](https://code.claude.com/docs/en/agent-sdk/mcp.md)
- Tool search activé par défaut : les définitions d'outils MCP sont différées et chargées à la demande pour économiser le contexte — [Connect to external tools with MCP](https://code.claude.com/docs/en/agent-sdk/mcp.md)
- Outils custom in-process : décorateur `@tool(name, description, schema)` (schéma = dict `{"lat": float}` ou JSON Schema complet) + `create_sdk_mcp_server(name, version, tools=[...])` passé à `mcp_servers={...}` ; le handler async renvoie `{"content": [...], "is_error": bool}` ; annotations `readOnlyHint` etc. ; « The Python `@tool` decorator forwards only `content` and `is_error` » (pas de `structuredContent` en Python in-process) ; la `permission_policy` par outil est TypeScript seulement — [Give Claude custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools.md)
- Streaming : deux modes. « Streaming Input Mode (Recommended) » via `ClaudeSDKClient` (session persistante, messages en file, interruption, « Real-time feedback: see responses as they're generated ») vs « Single Message Input » via `query()` (one-shot, sans images ni interruption) ; en Python, « `receive_response()` loop ends at the first result message » — [Streaming Input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode.md)
- Avertissement Python : « a generator exception is logged at debug level and the session stalls without raising » — [Streaming Input](https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode.md)

**OpenAI Agents SDK**
- « lightweight, easy-to-use package with very few abstractions », successeur « production-ready » de Swarm ; `pip install openai-agents` ; guardrails en parallèle, sessions (mémoire), tracing ; « Models section covers non-OpenAI providers » avec pages LiteLLM — [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)
- « Handoffs are represented as tools to the LLM » : un handoff vers `Refund Agent` apparaît comme `transfer_to_refund_agent` ; `handoff()` permet `on_handoff` (callback), `input_type` (schéma d'arguments validé), `input_filter` (ex. `handoff_filters.remove_all_tools`), `is_enabled` ; par défaut l'agent receveur voit tout l'historique ; « nested handoff history is an opt-in beta » — [Handoffs](https://openai.github.io/openai-agents-python/handoffs/)
- Différence clé : « A handoff transfers control, and the receiving agent takes over the conversation » ; pour un spécialiste imbriqué qui ne doit pas prendre la main : `Agent.as_tool(...)` — [Handoffs](https://openai.github.io/openai-agents-python/handoffs/)
- MCP : `MCPServerStdio`, `MCPServerStreamableHttp` (recommandé), `MCPServerSse` (« The MCP project has deprecated this transport »), `HostedMCPTool` (exécuté côté Responses API, OpenAI uniquement) ; `cache_tools_list=True` pour éviter un `list_tools()` par run ; filtres statiques/dynamiques — [MCP](https://openai.github.io/openai-agents-python/mcp/)
- Streaming : `Runner.run_streamed` + événements `run_item_stream_event` — [MCP](https://openai.github.io/openai-agents-python/mcp/)
- Une source secondaire rapporte « an April 2026 overhaul that added sandboxes and subagents » (non vérifié sur la doc officielle) — [WebSearch, résumé des comparatifs 2026](https://www.morphllm.com/ai-agent-framework)

**LangGraph / LangChain**
- La page multi-agents de LangChain décrit cinq patrons : **Subagents** (agent principal coordonne des sous-agents comme outils, sans état, forte isolation, bonne parallélisation), **Handoffs** (appels d'outils qui mettent à jour une variable d'état pour changer l'agent actif ; « handoffs run sequentially »), **Skills**, **Router** (classification puis dispatch vers un ou plusieurs agents, « stateless, so each request needs a routing call »), **Custom workflow** (LangGraph, mixant déterministe et agentique) — [LangChain multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- Handoffs LangChain/LangGraph : un outil de handoff renvoie un `Command` dont `update` écrit une variable d'état (`active_agent`, `current_step`) et ajoute un `ToolMessage` avec le `tool_call_id` correspondant (obligatoire) ; en multi-graphe, `Command(goto="sales_agent", graph=Command.PARENT)` fait le saut dans le graphe parent ; des fonctions de routage lisent `active_agent` ; alternative mono-agent : middleware `@wrap_model_call` qui remplace system prompt et outils via `request.override(...)` ; recommandation : ne transmettre que le dernier `AIMessage` + le `ToolMessage`, pas tout l'historique du sous-agent — [LangChain Handoffs](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs)
- Comparatifs 2026 : « LangGraph is an orchestration layer — you define a graph, it executes and persists it » ; à choisir « if the agent has to survive a crash mid-task » ; « overkill for a simple agent with two tools and a linear flow » — [WebSearch, comparatifs 2026](https://web-9ja.pages.dev/blog/langgraph-vs-openai-claude-agent-sdk-2026)

**Pydantic AI**
- Trois patrons multi-agents : **agent delegation** (un agent appelle un autre depuis un outil et reprend la main ; recommande la capacité Harness `SubAgents` qui expose un outil `delegate_task` ; passer `usage=ctx.usage` pour cumuler l'usage ; tools en `async def` car `run_sync()` lève `UserError` dans un outil), **programmatic agent hand-off** (le code applicatif décide quel agent tourne ensuite, contexte passé via `message_history`), **graph-based control flow** — [Pydantic AI multi-agent](https://pydantic.dev/docs/ai/guides/multi-agent-applications/)
- « Deep agents » : capacités harness = planning, filesystem/shell, sub-agent delegation, sandboxed execution, context compaction, tool approval, durable execution — [Pydantic AI multi-agent](https://pydantic.dev/docs/ai/guides/multi-agent-applications/)
- MCP client : `MCPToolset` (enveloppe le client FastMCP) accepte URL, script local, transports `StdioTransport`/`StreamableHttpTransport`/`SSETransport` (SSE « supported but deprecated »), ou un serveur FastMCP in-process ; `toolsets=` sur l'agent ; `load_mcp_toolsets()` depuis un JSON avec expansion `${VAR}` ; `.prefixed('name')` contre les collisions ; sampling et elicitation supportés ; flag `native=True` pour le support MCP natif du fournisseur — [Pydantic AI MCP client](https://pydantic.dev/docs/ai/mcp/client/)
- Comparatifs : « the type-safe option for smaller agents » ; « no graph executor, checkpointing or memory layer » (table secondaire) — [WebSearch, comparatifs 2026](https://www.alexcloudstar.com/blog/ai-agent-frameworks-comparison-2026)

**CrewAI**
- Flows : modèle « event-driven » (`@start()`, `@listen()`, `or_()`, `and_()`, `@router()`, `@human_feedback` ≥ 1.8.0), état Pydantic ou dict, `@persist` SQLite, reprise/fork ; `stream = True` fait renvoyer un itérable de chunks à `kickoff()` ; `flow.usage_metrics` agrège les tokens — [CrewAI Flows](https://docs.crewai.com/en/concepts/flows)
- MCP : liste `mcps` sur l'agent (`MCPServerStdio`, `MCPServerHTTP`, `MCPServerSSE`, ou URL `#tool_name`) ou `MCPServerAdapter` (`crewai-tools[mcp]`), timeout 30 s ; **limitation** : « "Prompts" and "resources" are not integrated as CrewAI components » ; sorties multimodales à gérer soi-même — [CrewAI MCP overview](https://docs.crewai.com/en/mcp/overview)
- Modèles : exemples en chaînes LiteLLM (`openai/gpt-4o-mini`), classe `LLM` — [CrewAI Flows](https://docs.crewai.com/en/concepts/flows)

**Vue d'ensemble (sources secondaires, à prendre avec recul)**
- « The landscape splits into two categories: provider-native SDKs (Claude, OpenAI, Google) ... and independent frameworks (LangGraph, CrewAI, Smolagents, Pydantic AI, AutoGen) that work across providers » ; conseil convergent : « if you are committed to one model provider, use its own SDK » — [WebSearch, comparatifs 2026](https://www.morphllm.com/ai-agent-framework)

### Inferences
- **Handoffs-as-tools** : seul l'OpenAI Agents SDK le formalise nativement (`transfer_to_x`). Dans le Claude Agent SDK, l'équivalent est l'outil `Agent` (sous-agent = appel d'outil dont seul le résumé final remonte) ; dans Pydantic AI, c'est `delegate_task` (harness SubAgents) ou un outil maison. Pour Friday, le patron « sous-agent comme outil » est préférable au « handoff qui prend la main » : le Conductor garde la voix et la continuité du dialogue, l'agent spécialisé ne parle jamais directement à l'utilisateur.
- **Claude Agent SDK pour Friday** : avantages = sous-agents déclaratifs avec modèle par agent (`model="haiku"` pour le monitor système, `"sonnet"`/`"opus"` pour le researcher), outils Friday exposés en 10 lignes via `@tool` + `create_sdk_mcp_server`, MCP externes (Home Assistant HTTP, Google Calendar/Gmail) par simple dict, permissions fines. Inconvénients = dépendance au binaire Claude Code (Node), sous-agents en arrière-plan par défaut (il faut dire au Conductor d'attendre), pas de `structuredContent` ni de `permission_policy` côté Python, outil `Workflow` TypeScript-only, et clause de licence (clé API obligatoire). Le mode `ClaudeSDKClient` est indispensable pour une session vocale persistante avec interruption.
- **Pydantic AI** est l'alternative neutre la plus proche des besoins : handoff programmatique = le Conductor en code peut court-circuiter le LLM pour les commandes fréquentes (voir Q5), typage strict des sorties, MCP via FastMCP (stdio/HTTP/in-process), 2.x publié le jour même de cette note (cadence élevée = maturité mais aussi churn d'API).
- **LangGraph** n'apporte sa valeur (checkpointing, reprise après crash) que si Friday doit persister des tâches longues ; pour un assistant vocal où la latence prime, le surcoût d'abstraction n'est pas justifié. **CrewAI** reste orienté « crews » de rôles et son MCP ne couvre que les tools ; peu adapté à un hub vocal.
- Aucune source primaire ne donne de chiffre de latence propre à un framework ; la latence sera dominée par le modèle et le nombre de tours (un sous-agent = au moins un aller-retour API supplémentaire).

### Gaps
- Handoffs LangGraph couverts via la page LangChain Handoffs ; le streaming LangGraph (modes de stream) et `langchain-mcp-adapters` n'ont pas été vérifiés sur une page officielle (anciennes URLs `langchain-ai.github.io/langgraph/...` redirigent vers une page vide, `docs.langchain.com/oss/python/langgraph/multi-agent` en 404).
- Pas de source officielle sur le support « agents as tools » / sub-agents dans l'OpenAI Agents SDK 0.24 au-delà de la page handoffs ; la mention d'« avril 2026 : sandboxes et subagents » vient d'un blog.
- Pas de page CrewAI consultée sur le « hierarchical process / manager agent » (les deux pages lues ne le mentionnent pas).
- Aucun benchmark de latence d'orchestration comparant ces cinq frameworks n'a été trouvé.

## Question 2 — MCP en 2026 : serveur Home Assistant, calendrier/e-mail, exposer les outils de Friday

### Takeaway
MCP est stabilisé sur deux transports (stdio et Streamable HTTP ; HTTP+SSE est déprécié depuis la spec 2025-03-26). Home Assistant expose un serveur MCP intégré (depuis 2025.2) en HTTP avec OAuth 2.0 PKCE ; Google fournit depuis mai 2026 des serveurs MCP hébergés Gmail et Calendar (Developer Preview). Les outils propres à Friday s'exposent soit in-process (Claude Agent SDK `@tool` / Pydantic AI FastMCP in-process), soit comme serveur MCP stdio autonome réutilisable par n'importe quel client.

### Cited Findings
- Spec MCP : « The protocol currently defines two standard transport mechanisms: stdio, Streamable HTTP » ; « Clients SHOULD support stdio whenever possible » ; Streamable HTTP « replaces the HTTP+SSE transport from protocol version 2024-11-05 » ; un seul endpoint POST+GET (ex. `https://example.com/mcp`), sessions via header `Mcp-Session-Id`, reprise via `Last-Event-ID`, header `MCP-Protocol-Version: 2025-06-18` ; avertissement sécurité : valider `Origin`, binder sur 127.0.0.1 en local — [MCP spec 2025-06-18, Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)
- Home Assistant « acts as an MCP server, letting AI agents such as Claude or ChatGPT view and control your home » ; deux « LLM APIs » : **Device control** (mêmes outils qu'Assist, limité aux entités exposées aux assistants vocaux) et **Home Assistant** (lecture de toutes les entités/logs/historique et toute action ; compte administrateur requis) ; ressource `homeassistant://assist/context-snapshot` (Device control seulement) ; endpoints `/api/mcp` et `/api/mcp/assist` ; auth OAuth 2.0 PKCE avec Client ID Metadata Documents, pas de client secret ; supporte Prompts, Tools, Resources ; « Not supported: Sampling and Notifications » ; introduit en HA 2025.2 ; options « Expose all AI tools » et « Require an administrator account » activées par défaut ; commande Claude Code : `claude mcp add --transport http home-assistant <url>` puis `claude mcp login home-assistant` — [Home Assistant MCP Server integration](https://www.home-assistant.io/integrations/mcp_server/)
- Google : serveur Calendar MCP officiel à `https://calendarmcp.googleapis.com/mcp/v1`, Gmail à `https://gmailmcp.googleapis.com/mcp/v1`, avec OAuth ; « Workspace MCP server: Gradual rollout starting May 1, 2026 » ; accès via le Google Workspace Developer Preview Program ; docs de configuration sur developers.google.com/workspace/{gmail,calendar}/api/guides/configure-mcp-server ; Google avertit sur l'injection de prompt indirecte depuis e-mails/documents — [Google Workspace Updates, mai 2026](https://workspaceupdates.googleblog.com/2026/05/agent-tools-and-security-updates-for-workspace-developers.html) ; détails d'outils via annuaire tiers — [developersdigest (Gmail)](https://www.developersdigest.tech/mcp-servers/google-workspace-gmail), [developersdigest (Calendar)](https://www.developersdigest.tech/mcp-servers/google-workspace-calendar)
- Alternative communautaire Python : `workspace-mcp` 1.16.1 sur PyPI — [PyPI workspace-mcp](https://pypi.org/project/workspace-mcp/1.16.1/)
- Claude Agent SDK : le SDK ne fait pas de flux OAuth interactif ; pour un serveur HTTP protégé, « complete the OAuth flow in your own application and pass the resulting access token in the server's `headers` », ou se connecter une fois depuis une session Claude Code interactive sur la même machine — [Connect to external tools with MCP](https://code.claude.com/docs/en/agent-sdk/mcp.md)
- Claude Agent SDK : « When a successful tool result with no image content is larger than 25,000 tokens, Claude Code saves the output to a file » (`MAX_MCP_OUTPUT_TOKENS`) — [Connect to external tools with MCP](https://code.claude.com/docs/en/agent-sdk/mcp.md)
- Exposer ses propres outils : Claude Agent SDK `@tool` + `create_sdk_mcp_server` (in-process, « not as a separate process ») — [Give Claude custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools.md) ; Pydantic AI `MCPToolset` accepte « an in-process FastMCP server » — [Pydantic AI MCP client](https://pydantic.dev/docs/ai/mcp/client/) ; SDK Python officiel `mcp` 2.3.0 — [PyPI mcp](https://pypi.org/pypi/mcp/json)
- API Claude directe (sans Agent SDK) : le connecteur MCP nécessite `mcp_servers=[{type:"url",...}]` **et** `tools=[{type:"mcp_toolset", mcp_server_name:...}]` avec le beta `mcp-client-2025-11-20` — [skill claude-api, section Common Pitfalls (doc locale Anthropic)](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)

### Inferences
- Pour Friday sur un Mac local, Home Assistant MCP en « Device control » (sans compte admin) est le périmètre sûr pour l'agent *home control* ; l'API « Home Assistant » complète donne historique et logs au *system monitor*, au prix d'un compte admin. L'absence de Sampling/Notifications côté HA signifie que les événements domotiques (porte ouverte, etc.) ne remonteront pas par MCP : il faut un canal séparé (WebSocket HA → bus d'événements Friday, voir Q5).
- L'OAuth PKCE de HA et des serveurs Google doit être géré par Friday lui-même (petit serveur de callback local, stockage du refresh token dans le trousseau macOS), puis le token injecté en `headers` du serveur MCP. C'est le même mécanisme pour les trois serveurs.
- Exposer les outils de Friday : l'in-process (`@tool`) est le plus simple et le plus rapide (pas de sous-processus) ; un serveur MCP stdio séparé (SDK `mcp`/FastMCP) est préférable si les mêmes outils doivent être réutilisés par Claude Desktop ou un autre client, ou si l'on veut `structuredContent` depuis Python.
- Le transport SSE est à proscrire pour tout nouveau serveur ; utiliser Streamable HTTP (`"type": "http"`).

### Gaps
- Je n'ai pas ouvert les pages officielles Google `configure-mcp-server` ; la liste exacte des outils Gmail/Calendar, les scopes et le statut (Preview vs GA en novembre 2026) viennent d'annuaires tiers.
- La page HA ne dit pas explicitement « Streamable HTTP » ; elle montre des endpoints HTTP et un `--transport http`, ce qui l'implique sans le confirmer.
- Pas de serveur MCP officiel Apple (Calendrier/Mail macOS) trouvé ; non recherché faute de budget d'appels.

## Question 3 — Modèles Claude actuels : noms, contexte, prix, TTFT, prompt caching, routage vs conversation

### Takeaway
Gamme actuelle (toutes 1M de contexte, 128K de sortie, cutoff juin 2026) : Haiku 5.5 (`claude-haiku-5-5`, 0,10 $/0,50 $ par MTok jusqu'à 100K de prompt, « Fastest »), Sonnet 5.5 (`claude-sonnet-5-5`, 2 $/10 $, « Fast »), Opus 5.5 (`claude-opus-5-5`, 4 $/20 $, « Moderate », modèle par défaut recommandé), Fable 5.2 (`claude-fable-5-2`, 8 $/40 $). Anthropic recommande explicitement **Haiku 5.5 à effort `low`** pour les applications sensibles à la latence (routage d'intention) ; pour la conversation, Sonnet 5.5 (vitesse + intelligence) ou Opus 5.5. Le prompt caching (min 512 tokens sur ces modèles, lecture à 0,05–0,10× le prix d'entrée) rend un long system prompt quasi gratuit en lecture. Aucun chiffre officiel de TTFT n'est publié ; les chiffres tiers sont contradictoires.

### Cited Findings

**Gamme et IDs**

Fable 5.2 n'est pas justifié pour un assistant vocal (prix double d'Opus 5.5, tours longs, exige rétention 30 jours).
- **Caching** : le system prompt de Friday (persona, règles, description des agents) dépasse facilement 512 tokens ; un seul breakpoint sur son dernier bloc + caching automatique pour l'historique suffisent. Garder `tools` strictement stables entre requêtes (le tool search du Claude Agent SDK aide, mais toute variation de la liste d'outils invalide tout le cache).

## Question 4 — Modèles locaux pour la classification d'intention sur Mac (Llama 3.x 8B, Qwen3, Gemma 3 via Ollama / MLX / llama.cpp)

### Takeaway
Sur Apple Silicon, un modèle 4B (Gemma 3 4B) tourne à ~150–180 tok/s et un 8B (Qwen3 8B, Llama 3.1 8B, Q4) à ~80–115 tok/s selon la puce (M4 Pro à M5 Max), d'après des benchmarks communautaires. MLX est le backend le plus rapide (1,1× à 3× llama.cpp selon les sources, surtout sur les MoE) ; Ollama a basculé sur un backend MLX en 2026 mais le réserve aux machines > 32 Go. Pour une simple classification d'intention, un 4B ou un 8B en Q4 (≈ 3–6 Go de RAM d'après la taille des fichiers) suffit, et une approche par embeddings (semantic-router) est encore plus rapide.

### Cited Findings
- M5 Max : Gemma 3 4B 178,7 tok/s ; Llama 3.1 8B 112,7 tok/s ; Qwen 3 8B 105,4 tok/s — [eval-apple-models, M5 Max benchmark](https://eval-apple-models.vercel.app/posts/m5-max-ai-model-benchmark/) ; tableau de bord : Gemma 3 4B-IT 179,4, Llama 3.1 8B 113,0 — [dashboard M5 Max](https://eval-apple-models.vercel.app/benchmarks/m5-max-ai-models/tools/dashboard/)
- M4 Max, Ollama v0.30.8 avec moteur MLX : Qwen 3 8B Q4_K_M 112 tok/s, Llama 3 8B Q4_K_M 104 tok/s — [markaicode, Ollama Qwen 3 M4 Max](https://markaicode.com/benchmarks/ollama-qwen-3-m4-max-latency-benchmark/)
- Tableau communautaire : Qwen 3 8B Q4_K_M 82 tok/s sur M4 Pro (Ollama) ; Llama 3.1 8B Q8_0 82 tok/s sur M5 Max — [llmcheck.net](https://llmcheck.net/benchmarks.html)
- « Ollama's Apple Silicon backend changed in 2026, so older 2025 numbers may not apply » — [markaicode, throughput](https://markaicode.com/benchmarks/ollama-qwen-3-m4-max-throughput-benchmark/)
- MLX vs llama.cpp : « about 1.4x over llama.cpp's Metal path on dense models and up to about 3x on mixture-of-experts models » ; Qwen3-Coder-30B-A3B ≈ 130 tok/s MLX vs 43 tok/s via Ollama/llama.cpp sur M4 Pro ; d'autres tests ne trouvent qu'environ 9 % d'écart sur les denses ; llama.cpp « 1.7–2.2x faster at prefill » — [WebSearch, résumé des sources MLX/Ollama 2026](https://levelup.gitconnected.com/ollama-mlx-nearly-doubles-llm-speed-on-your-mac-58-to-112-tok-s-and-your-old-models-get-none-of-fd1a9ec531fb) ; [Ollama Moves to MLX Backend](https://lilting.ch/en/articles/ollama-mlx-apple-silicon-preview)

- Versions : `mlx-lm` 0.32.2 (16/10/2026, Python ≥ 3.11), client `ollama` 0.6.3 — [PyPI](https://pypi.org/pypi/mlx-lm/json)
- Gemma 3 n'existe pas en 8B dans ces benchmarks ; la comparaison est 4B vs 8B — [WebSearch, résumé benchmarks Apple Silicon](https://eval-apple-models.vercel.app/posts/m5-max-ai-model-benchmark/)

### Inferences
- Pour classer une intention (sortie de 5–30 tokens), le débit de génération importe peu ; c'est le **prefill** (traitement du prompt) qui domine la latence, et llama.cpp est donné plus rapide que MLX sur ce poste. Avec un prompt de classification de ~500 tokens, un 4B–8B Q4 devrait répondre bien sous la seconde sur M-series récent (inférence à partir des débits cités ; non mesuré).
- Choix pragmatique : **Qwen3 8B Q4_K_M** (ou **Gemma 3 4B** si la RAM est limitée) via Ollama (API HTTP locale simple, client Python officiel) ; passer à `mlx-lm` seulement si l'on a > 32 Go ou si l'on veut le dernier backend. Les tailles de fichiers Q4 (≈ 2,5 Go pour 4B, ≈ 5 Go pour 8B) sont à vérifier sur les pages de modèles.
- Un modèle local 8B sert aussi de secours hors-ligne pour le routage et les commandes domotiques quand l'API Claude est injoignable.

### Gaps
- Aucune source primaire (Apple, Ollama, llama.cpp) consultée ; tous les chiffres sont communautaires, avec des puces, quantizations et versions hétérogènes.
- Pas de chiffre de **TTFT / temps de prefill** trouvé pour ces modèles sur Mac, ni de besoin RAM exact par modèle/quantization (la page tinyweights.dev n'a pas pu être chargée : DNS introuvable).

## Question 5 — Patrons : générateur-vérificateur (agent validateur), bus d'événements, routage d'intention sans LLM

### Takeaway
Anthropic documente le patron **evaluator-optimizer** (un appel génère, un autre évalue en boucle) et le patron **routing** (classifier puis dispatcher, « by an LLM or a traditional classifier »). Pour les commandes fréquentes, le routage par **embeddings** (semantic-router, pas d'appel LLM) est le standard ; un retour d'expérience Home Assistant rapporte ~95 % des commandes domotiques exécutées en < 500 ms. Le bus d'événements est un patron d'architecture (CrewAI Flows est explicitement « event-driven » ; Home Assistant MCP ne pousse pas de notifications, donc un bus interne est nécessaire).

### Cited Findings
- Patrons Anthropic (article du 19 déc. 2024, « much of the tooling landscape has changed since then ») : **Routing** = « An input is classified and sent to a specialized follow-up task, prompt, or tool », quand « the classification can be done accurately by an LLM or a traditional classifier », exemple : questions simples vers un modèle plus petit/moins cher ; **Orchestrator-workers** = « A central LLM breaks a task into subtasks, delegates them to worker LLMs, and synthesizes the results », pour les tâches dont les sous-tâches ne sont pas prévisibles ; **Evaluator-optimizer** = « One LLM call generates a response while another evaluates it and provides feedback, in a loop », quand il y a des critères d'évaluation clairs ; **Parallelization** (sectioning / voting) ; **Prompt chaining** avec « gates » programmatiques — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Semantic Router : « using vector embeddings to infer intent, reducing unnecessary LLM calls » (Thoughtworks Radar ; le blip n'est plus dans l'édition courante) — [Thoughtworks Radar, Semantic Router](https://www.thoughtworks.com/en-us/radar/tools/semantic-router) ; tutoriel : le routeur « decides which destination fits without calling an LLM », embeddings pré-calculés par route — [Towards AI, Semantic Router](https://pub.towardsai.net/semantic-router-the-ai-traffic-controller-4a55f7fe7c35) ; paquet `semantic-router` 1.1.2 (09/11/2026) — [PyPI](https://pypi.org/pypi/semantic-router/json)
- Retour d'expérience assistant vocal Home Assistant : « incoming intent is matched against embeddings to find the closest entity + action pair. No LLM involved at this stage », un petit LLM local gère les commandes composées, « ~95% of HA commands execute under 500ms » (auto-rapporté, non benchmarké) — [Home Assistant Community, Embedding based Voice Assistant Pipeline](https://community.home-assistant.io/t/embedding-based-voice-assistant-pipeline/991584)
- Limite des embeddings purs : « standard semantic similarity approaches tend to overweight common/shared terms and struggle with negative intent boundaries in low-data settings » — [Hugging Face forum](https://discuss.huggingface.co/t/mproving-intent-classification-with-overlapping-semantics-in-low-data-settings-non-llm-approaches/175203)
- Claim non sourcé « 100-1000x latency reduction » — [Bright Coding](https://prompts.brightcoding.dev/blog/semantic-router-why-top-devs-ditch-llm-agents-for-10ms-routing) (à ne pas reprendre tel quel)
- LangChain : le patron **Router** est « stateless, so each request needs a routing call » ; les **Handoffs** « run sequentially » ; les **Subagents** offrent « strong context isolation » et « parallel execution is strong » — [LangChain multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)
- CrewAI Flows : « event-driven model », `@listen`, `or_()`, `and_()`, `@router()` — [CrewAI Flows](https://docs.crewai.com/en/concepts/flows)
- Home Assistant MCP : « Not supported: Sampling and Notifications » — [Home Assistant MCP Server](https://www.home-assistant.io/integrations/mcp_server/)
- Claude Agent SDK : hooks « Run custom code at key points in the agent lifecycle » ; sous-agents en arrière-plan avec rapport à un tour ultérieur — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview), [Subagents](https://code.claude.com/docs/en/agent-sdk/subagents.md)
- Claude API : outil **advisor** (un modèle plus capable conseille l'exécuteur ; l'advisor doit être au moins aussi capable que le modèle principal, ex. exécuteur Sonnet 5.5 → advisor Opus 5.5) — [skill claude-api, section Common Pitfalls (doc locale Anthropic)](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool)
- Claude Agent SDK, annotations `readOnlyHint: true` : « Lets Claude batch this with other read-only calls » (parallélisme des outils sans effet de bord) — [Give Claude custom tools](https://code.claude.com/docs/en/agent-sdk/custom-tools.md)

### Inferences
- **Routage à trois étages pour Friday** : (1) embeddings locaux (semantic-router ou un petit encodeur) pour les commandes domotiques/système fréquentes, exécution directe sans LLM ; (2) Haiku 5.5 `low` (ou Qwen3 8B local en secours) pour classer tout ce qui tombe sous le seuil de similarité ; (3) Sonnet 5.5/Opus 5.5 pour la conversation et les agents lourds. Prévoir une marge de confiance et un fallback LLM pour les formulations négatives (« n'éteins pas… »), point faible documenté des embeddings.
- **Générateur-vérificateur** : implémentable soit comme sous-agent *validator* (Claude Agent SDK : un `AgentDefinition` read-only avec `tools=[...]` restreints, modèle Haiku/Sonnet), soit comme patron evaluator-optimizer en code (Pydantic AI : agent générateur + agent évaluateur typé, boucle bornée). À réserver aux sorties à critères vérifiables (code, commandes domotiques avant exécution, e-mails avant envoi) ; inutile pour la conversation courante où il doublerait la latence.
- **Bus d'événements** : nécessaire car MCP (HA) ne pousse rien ; un bus asyncio interne (ou Redis/NATS si multi-processus) reçoit les événements HA (WebSocket), les alertes du *system monitor* et les rappels du *scheduler*, et le Conductor décide quoi dire. Les sous-agents en arrière-plan du Claude Agent SDK se branchent naturellement dessus (le rapport arrive à un tour ultérieur) ; les hooks du SDK permettent de publier sur le bus à chaque appel d'outil.

### Gaps
- Aucune publication 2025–2026 comparant précision/latence des routeurs par embeddings vs petits LLM pour la commande vocale ; seuls des retours d'expérience.
- Aucune source officielle décrivant un « bus d'événements » dans les cinq frameworks hors CrewAI Flows ; c'est un patron d'architecture générale, pas une fonctionnalité de framework.
- Pas de source sur un agent validateur « générateur-vérificateur » tel quel dans la doc du Claude Agent SDK ; l'inférence s'appuie sur le patron evaluator-optimizer d'Anthropic et sur les restrictions d'outils des sous-agents.
